# Синхронизация MyTetra (десктоп) <-> MyTetroid (Android)

Черновик протокола. Статус: предложение для gee12, не реализовано.

## Прототип (октябрь 2026, ветка experimental-sco-new-features)

Серверная часть написана и проверена python-e2e против живого
приложения (16 проверок: auth, snapshot, push, record, blob,
traversal, pull, конфликты). Клиента пока нет.

Что внутри: `app/src/sync/` — `SyncCore` (ядро, общее для будущих
транспортов, включая локальный MCP), `SyncServer` (тонкий HTTP-адаптер
на QTcpServer), `SyncStore` (sidecar `syncstate.ini`, формат
mytetra.xml не тронут). Управление: `sync.ini` в рабочей директории
(`enabled`, `bind`, `port`, `token`, генерируется сам).

Осознанные упрощения прототипа, зафиксированные до клиента:

- Один клиент. Sidecar хранит одно последнее подтвержденное
  состояние, `since` в `/pull` принимается, но diff всегда против него.
- Ветки при конфликте last-writer-wins с пометкой в ответе,
  записи дублируются с тегом `conflict` (данные не теряются).
- Перемещение веток и удаления не синхронизируются.
- Обрыв соединения между touch и получением pull-ответа клиент
  не заметит (лечится серверным журналом в будущем).
- Шифрованные сущности без введенного пароля пропускаются
  с reason `crypt-locked`.
- Вид не дергается: вставка тихая, таблица обновится при следующем
  переходе по веткам (periodicCheck заметит новый mytetra.xml).

## Мотивация

Синхронизация на уровне файлов (git, syncthing) имеет две проблемы:

1. Android со scoped storage не дает одному приложению ходить в папку
   другого, общая папка для базы стала затруднительна.
2. Файловый синкер гоняется с работающим десктопом: приложение
   переписывает `mytetra.xml` при сохранении, синкер в этот момент
   может забрать или положить полуторное состояние.

Сервер внутри десктопа снимает обе проблемы: он читает модель данных
напрямую (гонок с сохранением нет), а телефону нужен только сетевой
доступ (песочнице Android он разрешен).

Мобильный клиент: MyTetroid (gee12, GPL v3). Клиентскую часть пишет
gee12 или PR от нас, сервер без клиента не имеет смысла.

## Архитектура

- Десктоп = сервер в LAN. Транспорт HTTP+JSON, свой код на QTcpServer
  (правило Qt-only, сторонних библиотек нет).
- Телефон = клиент, периодически опрашивает сервер (WorkManager),
  пуша в первой версии нет.
- Выход за пределы LAN (NAT, релей, аккаунты) сознательно вне скоупа.
  Сначала LAN, релей только если попросят.

## Единицы синхронизации

Уровень записей, не файлов:

- Ветка: id, parentId, поля (name, ctime...).
- Запись: id, branchId, поля (name, author, url, tags, ctime...),
  тело `text.html`, картинки, аттачи.
- Шифрованные ветки едут шифртекстом как есть, сервер открытый
  текст не видит и не может увидеть.

Каждая сторона хранит `lastSyncRev` (монотонный номер ревизии сервера).
Дельта считается по паре (mtime, хеш контента) каждой сущности.

## Эндпоинты (черновик)

- `GET /status` — версия протокола, rev сервера. Без авторизации,
  для обнаружения.
- `GET /snapshot` — дерево id + хеши, дешевая сверка "что изменилось".
- `GET /pull?since=<rev>` — изменения сервера после rev: upsert-список
  веток и записей (метаданные) без блобов.
- `GET /blob/<recordId>/<name>` — тело записи, картинки, аттачи.
- `POST /push` — изменения клиента: upsert-список + блобы
  multipart-частями. Сервер отвечает новым rev.
- Все, кроме `/status`, требуют `Authorization: Bearer <token>`.

## Pairing

- Десктоп в Tools -> Sync показывает QR: адрес, порт, токен,
  отпечаток TLS-сертификата.
- Мобила сканирует, запоминает, дальше ходит с Bearer.
- Самоподписанный TLS + пиннинг отпечатка (TOFU). Обычную проверку
  цепочки Android для самоподписа не пропустит, пиннинг решает.

## Конфликты

Правило одно: данные не теряются никогда.

- Менялась только одна сторона — применяется ее версия.
- Меняли обе после общего rev — создаются обе копии, копия клиента
  получает тег `conflict`, разруливает человек руками.
- Удаление против изменения — изменение побеждает, удаление
  превращается в тег `conflict-deleted` на копии. Удалять молча нельзя.

## Нерешенные вопросы

- Формат rev: счетчик сервера vs векторные часы. Для двух узлов
  хватает счетчика сервера + lastSyncRev клиента.
- Аттачи больше N МБ: качать лениво по запросу или сразу.
- Что считать mtime записи: правка тела, полей, картинок — любого.
