# MyTetra — формат БД на диске (контракт)

> Документ: `02_database_format.md`
> Источник: анализ кода (`models/tree/*`, `models/recordTable/*`,
> `models/dataBaseConfig/*`, `libraries/*`), ветка `experimental-synctetra`.
>
> **Этот формат обязан оставаться совместимым.** Любые изменения архитектуры
> не должны менять описанные здесь файлы, их структуру и семантику.

## 1. Общая структура

«База данных» MyTetra — это **каталог** (в конфиге `tetradir`, по умолчанию
`/opt/mytetra/data`). Признак того, что каталог является базой MyTetra
(`DatabasesManagementModel::isDbDirectory`):

```
<tetradir>/
├── mytetra.xml      # (обязательно) — структура дерева и метаданные записей
├── database.ini     # (обязательно) — настройки базы (версия, криптография)
└── base/            # (обязательно) — каталог с содержимым записей
```

Дополнительно в базе могут находиться каталоги, не участвующие в контракте,
например `icons/` (коллекция иконок веток) и `shared/` (демо-экспорт). MyTetra
не удаляет произвольные подкаталоги/файлы внутри `tetradir`, кроме штатных
операций.

Корзина — **отдельный** каталог (`trashdir`, по умолчанию `/opt/mytetra/trash`),
вне `tetradir`. В него перемещаются старые версии файлов.

## 2. `mytetra.xml`

Единый файл, описывающий **всё дерево** веток и **метаданные всех записей**.

### 2.1 Пример (эталонный файл из ресурсов)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mytetradoc>
<root>
 <format version="1" subversion="2"/>
 <content>
  <node id="1300000000aaaaaaaaa1" name="Rename me" crypt="">
   <recordtable>
    <record id="1300000000aaaaaaaaa3" name="Welcome to MyTetra!"
            author="" url="" tags="MyTetra, Qt" ctime="20081210124656"
            dir="1300000000aaaaaaaaa2" file="text.html"/>
   </recordtable>
   <node id="..." name="..." crypt="">
    <recordtable> ... </recordtable>
    <node ...>...</node>
   </node>
  </node>
 </content>
</root>
```

### 2.2 Структура

- **`<root>`** — корень документа.
- **`<format version="1" subversion="2"/>`** — версия формата
  (`CURRENT_FORMAT_VERSION 1`, `CURRENT_FORMAT_SUBVERSION 2` в `main.h`).
  Более новых версий программа не читает; миграция 1.1→1.2 — пустая.
  Обновление формата возможно только **аддитивно** и только через механизм
  `updateSubVersionFrom...`.
- **`<content>`** — единственный контейнер, содержит корневые `<node>`.
- **`<node>`** — ветка дерева. Атрибуты копируются из XML в `QMap` модели как
  есть (`TreeItem::setAllFieldDirect`). Допустимые поля ветки
  (`FixedParameters::itemFieldAvailableList`):
  `id`, `name`, `ctime`, `crypt`, `icon`.
  - `crypt="1"` — ветка (и вся её поддерево) зашифрована.
  - Внутри узла идут `<recordtable>` (таблица записей) и вложенные `<node>`.
- **`<recordtable>`** — таблица конечных записей ветки; может отсутствовать
  или быть пустой.
- **`<record>`** — запись. Атрибуты (сериализуемые «натуральные» поля,
  `FixedParameters::recordNaturalFieldAvailableList`):
  `id`, `name`, `author`, `url`, `tags`, `ctime`, `dir`, `file`, `crypt`, `block`.
  - Полный список полей записи (включая вычисляемые): `id, name, author, url,
    tags, ctime, dir, file, crypt, block, hasAttach, attachCount`.
  - Вычисляемые (`hasAttach`, `attachCount`) в XML **не пишутся**.
  - `dir` — короткое имя подкаталога в `base/` (полный путь:
    `<tetradir>/base/<dir>/`).
  - `file` — имя файла записи (обычно всегда `text.html`).
  - `ctime` — время создания записи, формат `yyyymmddhhmmss` (в коде
    `"yyyyMMddhhmmss"`). **Поля mtime в формате нет.**
  - `crypt="1"` — поля записи и её файлы зашифрованы.
  - `block="1"` — запись заблокирована от редактирования.
- **`<files><file .../></files>`** — вложенный элемент записи для **вложений**
  (`Attach`). Атрибуты файла-вложения: `fileName` (человекочитаемое имя),
  `type` (`file` или `link`), `id`, `crypt`.
  Признак «есть вложения» в XML: подэлемент `<files>` у `<record>`.

### 2.3 Загрузка и сохранение

Загрузка: `KnowTreeModel::initFromXML` → `XmlTree::load` (DOM через
`QDomDocument::setContent`), затем `init()` строит дерево `TreeItem`
рекурсией по `<content>/<node>` (`parseNodeElement`).

Сохранение: `KnowTreeModel::save()`:

1. Текущий `mytetra.xml` **перемещается в корзину**
   (`DiskHelper::removeFileToTrash` → `trash/<uniqueId>_mytetra.xml`);
2. Создаётся новый файл на том же пути;
3. Дерево сериализуется целиком через `QXmlStreamWriter` (UTF-8,
   авто-форматирование, `<!DOCTYPE mytetradoc>`, `<root>`, `<format .../>`,
   затем рекурсивный обход).

**Без файловой блокировки. Не атомарно** (есть окно, когда файла нет).
Старая версия сохраняется только в корзине.

## 3. `base/` — каталоги записей

Каждая запись имеет подкаталог в `<tetradir>/base/<dir>/`. Что там живёт:

| Файл | Назначение | Кто ссылается |
|------|------------|---------------|
| `text.html` | тело заметки (Qt HTML, UTF-8) | атрибут `file` записи |
| `image<id>.png` | картинки, вставленные в заметку | **никто в XML** — обнаруживаются сканированием `*.png` при загрузке; «осиротевшие» удаляются при сохранении |
| `<attachId>.<ext>` | файлы-вложения (`type="file"`) | метаданные `<files><file/>`; имя файла строится по `id` вложения |

**Особенности:**

- Именование файла вложения (внутреннее): `<attachId>` + расширение исходного
  файла (или без расширения в крайних случаях).
- Вложения типа `link` файл в базе **не имеют** — хранится абсолютная ссылка.
- Каталоги записей MyTetra копирует **целиком** при экспорте ветки и
  вычищает лишние `.png` при сохранении текста. Поэтому дополнительные файлы
  внутри `base/<dir>/` в целом допустимы, но **записей о них в формате нет**.

Создание каталога: `Record::checkAndFillFileDir` (mkdir при отсутствии).
При открытии записи, если файл `text.html` пропал, программа создаёт пустой.
Удаление записи: `RecordTableData::deleteRecord` → файлы каталога по одному
перемещаются в корзину (префикс `<uniqueId>_`), каталог удаляется.

## 4. `database.ini`

Настройки базы, формат INI `QSettings::IniFormat`, UTF-8, пишутся через
`DataBaseConfig`.

```ini
[General]
version=1
crypt_mode=0
crypt_check_salt=
crypt_check_hash=
middle_hash_check_data=
```

| Поле | Смысл |
|------|-------|
| `version` | версия формата этого ini (управляется миграциями) |
| `crypt_mode` | `0` — пароля нет; `1` — пароль задан и есть зашифрованные данные |
| `crypt_check_salt` | случайная соль (32 байта, Base64) для проверки пароля |
| `crypt_check_hash` | PBKDF2-хеш пароля (salt выше, 1000 раундов, 160 бит) — проверка введённого пароля без расшифровки |
| `middle_hash_check_data` | RC5-зашифрованная константа проверки локально сохранённого хеша пароля |

Если `database.ini` отсутствует — создаётся с этими значениями по умолчанию.

## 5. Идентификаторы

`UniqueIdHelper::getUniqueId()`:

```
<10-значный unix timestamp в секундах> + <10 случайных символов [0-9a-z]>
```

Пример: `1300000000aaaaaaaaa1`, `1789240647fxsoge5a89`.

Сиды генератора случайных чисел инициализируются от позиции курсора при старте
приложения. При вставке/копировании дубликаты ID в локальной памяти
перегенерируются (`KnowTreeModel::getAttributeTranslateTable`). **Глобальной
дедупликации между машинами нет** — потенциальная (малая) вероятность
коллизий на разных узлах.

Имя изображения: `image<getUniqueId()>.png`.

## 6. Корзина

- Путь: `trashdir` (отдельный каталог, не синкается с БД).
- Перемещение = `QFile::rename` с переименованием в `<uniqueId>_<исходное имя>`.
- Контроль лимитов: `TrashMonitoring` удаляет самые старые файлы, если число
  файлов > `trashmaxfilecount` (по умолч. 200) или объём > `trashsize` (по
  умолч. 5 МБ).
- В корзину попадают: старый `mytetra.xml` при каждом сохранении дерева,
  удалённые каталоги записей, осиротевшие картинки, резервные копии конфигов.

## 7. Шифрование

Только для зашифрованных веток (`crypt=1`), рекурсивно на всё поддерево.

### 7.1 Криптография

- Ключ: пароль → PBKDF2 (соль, 1000 раундов, 160 бит) — «middle hash»;
  фактический ключ RC5 = `MD5(middleHash)`.
- Алгоритм блочного: **RC5** (`RC5Simple.cpp`); строковые обёртки
  `CryptService` (Base64-транспорт при кодировании строк).
- Файлы шифруются **на месте** (чтение всего файла → RC5 → запись).

### 7.2 Что шифруется, а что нет

| Объект | Шифруется |
|--------|-----------|
| Поля ветки | `name`, `icon` (не шифруются: `id`, `ctime`, `crypt`) |
| Поля записи | `name`, `author`, `url`, `tags` (не шифруются: `id`, `dir`, `file`, `ctime`, `crypt`, `block`) |
| Файл записи (`text.html`) | содержимое целиком (имя файла остаётся) |
| Файлы-вложения | содержимое (`type="file"`); поля `fileName`, `link` шифруются; `id`, `type`, `crypt` — нет |
| Имена каталогов/файлов | **не** шифруются |

Вывод: зашифрованная запись для слепого читателя — это набор бинарных blob-ов;
метаданные для слияния (id, dir, file, ctime) остаются открытыми, но текстовые
поля и содержимое без пароля прочитать/проверить нельзя.

### 7.3 Паспортные точки

- Шифрование/расшифровка ветки: `TreeItem::switchToEncrypt/switchToDecrypt`.
- Повторное шифрование при смене пароля: `KnowTreeModel::reEncrypt`.
- Экспорт/импорт веток автоматически расшифровывает/шифрует данные.
- `database.ini` (crypt_check_*) — **локальное** свойство базы: ключ и проверка
  пароля на каждой машине свои.

## 8. Версии формата и миграции

- `format version="1" subversion="1"` → `1.2`: миграция пустая (никаких данных
  не меняет).
- Версия в `database.ini` обновляется механизмом миграций `DataBaseConfig`.
- `conf.ini` (приложение, не БД) имеет собственную систему версионных таблиц
  параметров (`AppConfig::get_parameter_table_N`), текущая — v42.
- `knownbases.ini` (список известных баз, не БД): секции `num0..numN`, поля
  `dbPath`, `trashPath`, `descript`; миграции v1→v2.

## 9. Что разрешено/не разрешено менять архитектуре

**Запрещено менять:**

- Структуру и атрибуты `mytetra.xml`, `base/<dir>/`, `database.ini`, корзины —
  их читает и пишет существующий код.
- Семантику ID, `ctime`, кодировок, шифрования содержимого.

**Разрешено (аддитивно):**

- Добавлять **новые файлы/каталоги внутри `tetradir`** вне `base/` и вне
  контрактных файлов (пример: уже существующий каталог `icons/`) — при условии,
  что `isDbDirectory` и существующая логика их игнорируют.
- Добавлять файлы в каталог записи `base/<dir>/` (переносится при экспорте,
  но по формату не отслеживается).
- Изменять внутренние механизмы записи (атомарность, очерёдность) **не меняя
  конечного вида файлов**.

Ограничение для sidecar-данных синхронизации: каталог на вершине `tetradir`
может быть залит в синхронизацию; содержимое `base/` копируется целиком при
экспорте веток, поэтому специфические служебные файлы лучше держать НЕ внутри
`base/`, а в отдельном каталоге (например `<tetradir>/.sync/`).
