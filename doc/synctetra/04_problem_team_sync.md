# MyTetra — постановка задачи: командная работа и обмен удалёнными БД-ветками

> Документ: `04_problem_team_sync.md`
> Статус: актуализирован под подписочную модель (2026-09-13).

## 1. Исходная ситуация

MyTetra задумана как **персональный** накопитель информации. Хранение —
«единый whole-file `mytetra.xml` + каталоги записей `base/<id>/`»; запись
рассчитана на одного активного редактора.

## 2. Первая попытка (master-master) — отклонена

Рассматривался вариант «несколько человек редактируют один реплицируемый
Syncthing каталог БД» (master-master). Анализ показал **принципиальную
несостоятельность** этого подхода в рамках Syncthing + текущей архитектуры:

1. `mytetra.xml` перезаписывается **целиком** при каждом метаданном изменении
   (`KnowTreeModel::save()`) → гонки двух узлов дают конфликт-копии Syncthing,
   которые MyTetra не читает.
2. Запись **неатомарна** (move в корзину → создание заново) → окно отсутствия
   файла, риск синхронизации удаления/частичного файла.
3. Нет координации между узлами, нет понятия владельца, нет журнала слияния.
4. Мониторинг внешних изменений следит только за mtime `mytetra.xml`,
   изменения `base/` другими узлами не видны.
5. `database.ini` машинно-специфичен (криптография) — синхронизировать нельзя.
6. Шифрованные ветки нельзя слепо сливать.

**Вывод:** безопасная коллективная работа в такой модели неосуществима
без полной переделки формата, что запрещено. Модель отклонена.

## 3. Желаемое состояние (требования, согласованные с владельцем)

Принята **подписочная модель + local-first данные**:

- **R1.** Основная БД каждого участника остаётся локальной, личной и
  реплицируется **никогда**. Формат БД сохраняется без изменений.
- **R2.** Обмен «кусками БД» = **публикация веток** в отдельный каталог
  `shared/` (по умолчанию рядом с бинарником), который целиком синхронизируется
  Syncthing.
- **R3.** Подписка: участник по желанию подписывается на опубликованную ветку,
  она отображается в панели **«Подписки»** (левая колонка, вне дерева БД) как
  **read-only** запись **с именем владельца**.
- **R4.** Подписчик не редактирует подписанную ветку напрямую, но может
  **импортировать** её (или выбранные изменения) в свою БД.
- **R5.** Обновления владельца видны подписчикам как **список изменений**
  («что конкретно поменялось»). Выбор изменений для импорта — вручную.
- **R6.** **Автоимпорт запрещён.** Особенно автосогласие с удалениями.
- **R7.** Инструмент версионирования/диффов обмена — **внешний `git`**
  (per-branch репозитории внутри `shared/`).
- **R8.** Узел без сети и без команды работает как обычная одиночная MyTetra.

## 4. Оставшиеся проблемы и как их решает подписка

| Проблема | Решение |
|----------|---------|
| Конфликты whole-file `mytetra.xml` | БД никогда не реплицируется; публикация — отдельный каталог |
| Неатомарность записи | остаётся риском только внутри личной БД; для обмена не существенна (публикация пересобирается целая) |
| Неатомарность публикации | пересборка `shared/<ownerDir>/<branchId>/` с техникой temp+rename в пределах каталога перед commit |
| «Что изменилось» | git diff + семантический парсер фрагментов (`BranchDiffEngine`) |
| Кто что изменил / имя владельца | git-идентичность + `meta.json` (имя/email), метка в дереве |
| Чужие правки попадают в мою БД против воли | только явный выборочный импорт; автоимпорта нет |
| Риск «согласиться с удалением» | удаления помечаются как «опасные», не выбраны по умолчанию, требуют согласия и идут через корзину |
| Чтение зашифрованных данных другими | публикация только в расширенной форме с согласия владельца (или запрет публикации) |
| `database.ini` в синке | не синхронизируется (вне обмена) |
| Два писателя в `shared/` | только владелец пишет в свою `shared/<ownerDir>/<branchId>/`; per-branch git-репозиторий |
| Синхронизация корзины/конфигов | не входят в обмен; при синхронизации родителя — `.stignore` |

## 5. Развёрнутые сценарии (use cases)

| № | Сценарий | Требование |
|---|----------|------------|
| UC-1 | Владелец публикует ветку; подписчик видит её read-only с именем владельца | R2, R3 |
| UC-2 | Владелец обновил/добавил записи | R5: подписчик видит «N изменений» |
| UC-3 | Владелец удалил запись | R6: «опасное» изменение, не выбрано по умолчанию, импорт с подтверждением и корзиной |
| UC-4 | Подписчик импортирует ветку в свою БД как часть своей | R4: обычная копия в личной БД |
| UC-5 | Подписчик правил уже импортированную запись, владелец её изменил | конфликт: «заменить / сохранить обе» |
| UC-6 | Публикация удалена владельцем | у подписчика метка «недоступна», импорт-копии остаются |
| UC-7 | Узел офлайн, потом возвращается | локальные правки и послать публикацию позже; синхронизация Syncthing сама всё приносит |
| UC-8 | Git отсутствует у подписчика | просмотр среза работает; публикация/дифф — с подсказкой |
| UC-9 | Шифрованная ветка предложена к публикации | подтверждение расшифровки при экспорте; либо запрет |

## 6. Объём работ (контур)

1. **Профиль команды и `shareddir`** (настройки, идентичность).
2. **Публикация** (экспорт ветки → `shared/<ownerDir>/<branchId>/` + `meta.json` +
   git commit).
3. **Подписки** (watcher, панель «Подписки» с именем владельца,
    baseline).
4. **Разность** («что изменилось»): git + семантический парсер.
5. **Выборочный импорт** (с проверками и корзиной; запрет автоимпорта).
6. **Документация Syncthing** и тесты.

Детальный дизайн — `05_design_proposal.md`, `06_shared_branch_exchange.md`.
План работ — `07_action_plan.md`.
