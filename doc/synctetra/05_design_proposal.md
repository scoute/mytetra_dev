# MyTetra — концепция новой архитектуры: командная работа (v2)

> Документ: `05_design_proposal.md`
> Статус: **принемается** — концепция по подписочной модели и local-first данным
> (заменяет черновик v1 от 2026-09-12, отклонённый по рискам master-master).

## 1. Суть решения

> Примечание (2026-09-13). Первоначальный макет с per-branch `.git` внутри
> каталогов публикаций (ниже, §4–§6) заменён двухзональной схемой
> `shared/sync/` + единый локальный `shared/.git` (ADR-015 в `08`); разность
> строится по диджестам. Актуальная структура каталога — `06`, §2.
>
> Примечание (2026-09-15, ADR-016). Добавлена авторитетная зона `shared/local/`
> (сборка вне `sync/`, source of truth, дубль 2x copy-changed) + `shared/.tmp/`
> + `changelog.json` в публикации + дисциплина двух коммитов
> (`local/` → `sync/` с гардом целостности). `mv local -> sync` запрещён.
> Восстановление `sync/` у владельца первично из `local/`. Детали — `06`.

Отказываемся от «нескольких редакторов одного синхронизируемого каталога БД»
(master-master). Это принципиально не решаемо безопасно в рамках Syncthing и
whole-file `mytetra.xml`.

Принятая модель: **подписка + local-first данные**.

1. **Основная БД каждого участника — локальная и личная.** Она никогда не
   синхронизируется. Значит, конфликты `mytetra.xml`, неатомарность и гонки
   внутри общей БД просто исчезают — их объекта больше нет.
2. **Обмен = публикация веток.** Чтобы поделиться веткой, владелец **экспортирует**
   её в отдельный каталог **`shared/`** (по умолчанию на том же уровне, где
   бинарник, путь настраивается). Каталог `shared/` целиком реплицируется
   Syncthing между участниками команды.
3. **Подписка.** Участники видят, какие ветки опубликованы; подписаться может
   любой. Подписки отображаются в отдельной **панели «Подписки»** (левая
   колонка, вне дерева БД — корень модели не трогается) как **read-only**
   записи с именем владельца. Редактировать их напрямую нельзя.
4. **Импорт — только вручную и выборочно.** Подписчик видит, что именно
   изменилось у владельца, и сам выбирает, какие изменения импортировать в свою
   БД. Автоимпорт, особенно автосогласие с удалениями, — запрещён.
5. **Инструмент версионирования обмена — внешний `git`** (по одному репозиторию
   на ветку внутр‹ каталога публикации). Git хранит историю и даёт диффы,
   по которым строится «что поменялось». Подробный выбор инструмента —
   в `06_shared_branch_exchange.md`.

Формат БД **не меняется ни в одной точке**: правки `mytetra.xml`, `base/`,
`database.ini` не производятся механизмами обмена вообще.

## 2. Терминология (кратко)

| Термин | Значение |
|--------|----------|
| **publication (публикация)** | каталог ветки в `shared/`, сгенерированный владельцем |
| **subscription (подписка)** | read-only запись в панели «Подписки», связанная с publication |
| **baseline** | состояние (commit) publication, на которое ориентируется подписчик («что я видел/импортировал последний раз») |
| **change (изменение)** | единица разности между baseline и текущим состоянием publication (запись добавлена/изменена/удалена и т. д.) |
| **import** | перенос выбранных изменений в личную БД подписчика (вручную) |

## 3. Принципы

1. **P1. БД — local-first.** Личная БД — единственный источник правды для её
   владельца и никогда не реплицируется.
2. **P2. `shared/` — только публикации.** В `shared/` пишут только владельцы
   публикаций и только в свой каталог ветки. Никакой общей «доски», никаких
   файлов с общим доступом на запись.
3. **P3. Один писатель публикации.** Каталог
   `shared/<ownerId>_<ownerName>/<branchId>_<name>/` пишет только
   владелец ветки → конфликтов записи нет (кроме экзотики, см. раздел 7).
4. **P4. Подписка не меняет чужое.** Подписчик никогда не пишет в публикацию;
   его действия локальны (вайчей отображение + импорт в свою БД).
5. **P5. Никакого автоимпорта.** Импорт, особенно удалений, — только явное
   действие пользователя, с подтверждением и наглядной разницей.
6. **P6. Формат не трогаем.** Обменник работает на уровне «фрагмент XML в
   синтаксисе mytetra.xml + каталоги записей» и на диск БД подписчика влияет
   только импортом через штатные механизмы.
7. **P7. Владелец виден.** В метаданных публикации фиксируется имя владельца;
   подписки отображаются с его именем.

## 4. Картина обмена (взаимодействие участников)

```

  └── ветка X                            └── (личные ветки B)

    branch.xml, records/,      meta.json, changelog.json, manifest)

```

## 5. Компоненты новой архитектуры

### 5.1 Служебные данные приложения (не БД, формат не затрагивается)

- **Профиль команды** (имя владельца, git-идентичность): ключи в `conf.ini`
  (`teamname`, `teamemail`) + эквивалент профиля на уровне git-identity.
- **Каталог обмена**: ключ `shareddir` в `conf.ini`. По умолчанию
  `<каталог бинарника>/shared`; если каталог бинарника недоступен для записи —
  фоллбэк `<рабочий каталог>/shared` с уведомлением.
- **Индекс подписок**: `<рабочий каталог>/subscriptions.ini` (QSettings, по
  образцу `knownbases.ini`): для каждой ветки — `branchId`, путь в `shared/`,
  `baselineCommit`, карта «sharedRecordId → localRecordId» и снапшот-хеши.

### 5.2 Новые модули (целевой набор)

| Класс | Назначение |
|-------|-----------|
| `TeamProfile` | чтение/редактирование профиля (имя, email), привязка к git-identity |
| `SharedDirWatcher` | отслеживание `shared/`: появление/изменение/исчезновение публикаций (сканирование двух уровней: каталог владельца → каталог публикации; QFileSystemWatcher + страховочный таймер) |
| `BranchPublisher` | генерация каталога публикации из ветки (экспорт + метаданные) + публикация/обновление |
| `BranchPublicationMeta` | чтение/запись `meta.json` публикации |
| `GitWrapper` | запуск внешнего `git` через `CommandRunner` (init/add/commit/log/diff/status), парсинг вывода |
| `SubscriptionRegistry` | индекс подписок (п. 5.1): подписка/отписка, baseline, карта импортированных записей |
| `SubscriptionPanel` | панель «Подписки» в левой колонке: группы «Подписки»/«Доступно», подписка/отписка, детект обновлений |
| `BranchSliceDialog` | диалог просмотра среза (только чтение): дерево записей по `branch.xml`, текст из `records/<dir>/<file>` |
| `PublishedBadgeDelegate` | бейдж «рука» на опубликованных ветках владельца в дереве |
| `BranchDiffEngine` | семантическая разность между двух XML-фрагментов (+ данные git): изменения записей/веток |
| `SubscriptionImportEngine` | выборочный импорт изменений в личную БД (добавить/заменить/удалить с проверками) |
| `ChangeViewDialog` (view) | UI «что изменилось»: список изменений, чекбоксы, детали, кнопки импорта |
| `Clipper` | веб-клиппер: глобальный хоткей (X11) / кнопка «Clip now» → HTML/текст/картинка из буфера в `unsorted_notes` с дедупом по sha256 (см. §11) |

### 5.3 Разделение ответственности

- **Git** — только хранилище версий и диффы файлов: «у кого что изменилось»,
  авторы, история. Никакой семантики нашего формата git не знает.
- **`BranchDiffEngine`** — переводит разность версий в «человеческие» изменения
  на уровне записей (парсит XML-фрагменты, сравнивает поля и содержимое).
- **`SubscriptionImportEngine`** — применяет выбранные изменения к личной БД
  через штатные механизмы (создание/замена записи, перенос файлов в корзину
  при удалении, детект локальных правок).

## 6. Основные потоки

### 6.1 Публикация ветки (владелец)

1. В дереве: «Опубликовать в общую папку…» на ветке;
2. проверка: ветка не должна быть вложена в другую публикацию; при
   шифровании — предупреждение (публикация идёт в расшифрованном виде, как при
   обычном экспорте) и явное согласие;
3. `BranchPublisher`: сборка `shared/<ownerId>_<ownerName>/<branchId>_<title>/`
   (при пустом профиле — в плоской `shared/<branchId>_<title>/`):
   - `branch.xml` — фрагмент ветки в **синтаксисе `mytetra.xml`**
     (переиспользование сериализации `KnowTreeModel`);
   - `records/<dir>/*` — копии каталогов записей (расшифрованные при
     необходимости);
   - `meta.json` — `branchId`, `title`, `ownerName`, `ownerId`,
     `publishVersion`, `publishedAt`;
4. `GitWrapper`: `git init` (если ещё нет), `git add -A`, commit
   «Публикация/Обновление <title>»; git-идентичность из профиля;
5. Syncthing разносит каталог на всех участников.

Обновление = тот же процесс (перезапись `branch.xml`, изменённых записей;
`git add -A; git commit`). Имя каталога владельца = `<ownerId>_<ownerName>`
(машинный ключ — `ownerId` до первого `_`), имя каталога публикации =
`<branchId>_<title>`: машинный ключ — `branchId` до первого `_`, часть с именем
фиксируется при первой публикации; каталоги **не переименовываются** даже при
переименовании ветки/профиля (актуальный заголовок — в `meta.json.title`,
имя владельца — в `meta.json.ownerName`).

### 6.2 Подписка (подписчик)

1. `SharedDirWatcher` находит новый каталог публикации (читает `meta.json`);
2. в панели «Подписки» появляется запись публикации в группе **«Доступно»**;
3. «Подписаться» → `SubscriptionRegistry` фиксирует подписку, `baselineCommit`
   = текущий HEAD публикации;
4. подписка появляется в группе **«Подписки»** как запись `X — Иван`:
   **read-only**, позже (Фаза 3.5) — по клику открывается содержание записей
   из `shared/`, редактор заблокирован, контекст-меню импорта активно.

Отписка: убрать секцию view; локальные данные не трогаются.

### 6.3 Детект изменений владельца

1. `SharedDirWatcher` ловит изменение `shared/<ownerDir>/<branchId>/`
   (или git HEAD);
2. `GitWrapper`: `git diff baselineCommit..HEAD --stat` и `--name-status`,
   затем `git show HEAD:branch.xml` и `git show baselineCommit:branch.xml`;
3. `BranchDiffEngine` строит список изменений (см. 6.4);
4. в дереве у подписки появляется бейдж «доступны изменения»; открывается
   диалог изменений (по желанию).

### 6.4 Что считается «изменением» (семантическая разность)

Для каждой пары фрагментов ветки (baseline и HEAD):

- изменение **названия/полей ветки**;
- **добавлена запись** (новый `id`);
- **изменена запись** — поля (`name`, `author`, `url`, `tags`) и/или содержимое
  `text.html` (по hash), вложения (`<files>`);
- **удалена запись** (id исчез) — помечается как «опасное»;
- **изменена структура** (ветка/подветка перемещена, переименована).

Каждый пункт: тип, адрес (ветка/запись), заголовок, краткое описание,
размер файлов, степень опасности (deletion = danger).

### 6.5 Выборочный импорт (подписчик)

1. Пользователь отмечает нужные изменения чекбоксами (удаления — отдельно,
   с явным согласием «Я понимаю, что удаляю данные»);
2. выбирается целевая ветка в личной БД (по умолчанию — ранее импортированная
   копия этой публикации);
3. `SubscriptionImportEngine`:
   - **добавить** — создаёт запись в БД через штатные механизмы
     (новый локальный `id`/`dir`; карта `sharedRecordId → localRecordId`
     сохраняется в индексе подписки);
   - **изменить** — находит локальную запись по карте; если её снапшот-хеш
     изменился (подписчик успел поправить) — конфликт: предложить «заменить /
     сохранить обе копии»; иначе заменить содержимое и поля;
   - **удалить** — только после явного согласия; сначала копия в корзину
     подписчика;
4. `baselineCommit` обновляется до HEAD после импорта (или после
   «отметить просмотренным»).

### 6.6 Отзыв/удаление публикации владельцем

Удаление каталога `shared/<ownerDir>/<branchId>/` (или его метки в
`meta.json`) → подписчики видят «публикация больше не доступна». Уже
импортированные копии у подписчиков остаются. Удаление публикации — только
владельцем; репликация удалений Syncthing распространяет (это безопасно:
локальные БД не затронуты).

## 7. Краевые случаи и их обработка

| Случай | Обработка |
|--------|-----------|
| Два владельца опубликовали ветки с одинаковым `branchId` | `branchId` уникален локально; при подписке проверяется уникальность в индексе подписок; дубликат помечается и показывается, импорт работает с каждым отдельно |
| Владелец удалил запись, подписчик её уже импортировал и правил | удаление в публикации → «опасное» изменение; импорт требует явного согласия; локальная правка → сначала конфликт-предупреждение |
| Git недоступен на машине подписчика | подписка работает на текущем срезе (без истории «что изменилось»); публикация требует git и показывает понятную подсказку |
| Шифрованная ветка | публикация только в расшифрованном виде (как экспорт); либо публикация запрещена настройкой для этой ветки |
| Большие вложения / рост `.git` | кнопка «Архивировать и сжать» (git gc / new baseline commit); предупреждения о размере; рекомендация не публиковать тяжёлые вложения |
| Синхронизация частичная (Syncthing не успел) | метки изменений появляются после схождения; повторный diff идемпотентен |
| Подписчик лишил ветку приватно и хочет оставить копию | отписка не удаляет импортированную копию |

## 8. Сохранение формата БД (P6)

- `mytetra.xml`, `base/`, `database.ini`, корзина **не модифицируются** ни одним
  из механизмов обмена.
- Публикация — это отдельный каталог `shared/` (вне БД), в синтаксисе,
  совместимом с `mytetra.xml`.
- Импорт в личную БД — только через штатные операции создания/замены записей и
  веток (те же, что использует обычный пользователь).
- БД, созданная новой версией, открывается старой: в ней нет ничего, чего бы
  не было раньше (профиль и индекс подписок живут в `conf.ini` и рабочем
  каталоге, не в БД).

## 9. Отклонённые альтернативы (кратко)

1. **Master-master одного каталога БД (v1)** — конфликты whole-file XML,
   неатомарность, гонки — отклонено (см. `04_problem_team_sync.md`).
2. **CRDT/OT-соредактирование** — не нужно сценарию, слишком сложно.
3. **Внутренний журнал/снапшоты вместо git** — дороже в поддержке, хуже в
   истории и диффах; git выбран внешним инструментом обмена (анализ —
   в `06_shared_branch_exchange.md`, раздел 4).

## 11. Веб-клиппер (вне обмена, личный инструмент)

- **Сценарий:** пользователь копирует фрагмент веб-страницы в браузерном
  аддоне (аддон — вне репозитория) и нажимает глобальный хоткей
  (`Ctrl+Alt+V`, X11) либо кнопку «Clip now» в настройках; HTML/текст/картинка
  из буфера обмена сохраняется новой записью в ветку `unsorted_notes`
  (создаётся в корне при первом использовании, id запоминается в
  `clipperbranchid` и переживает переименования).
- **Вставка** — штатным путём модели (`Record` FAT → `insertNewRecord` →
  PNG картинок в каталог записи → `saveKnowTree`), нормализация HTML через
  `QTextDocument` как при ручной вставке; внешние картинки докачиваются
  (таймаут 15 с), прямые картинки буфера кладутся как есть.
- **Дедуп:** sha256 нормализованного HTML против свежих 2000 текстов ветки
  (читаются с диска); повтор молча пропускается. Заголовок — первая непустая
  строка (до 80 символов), иначе `Clip <дата>`.
- **Зависимости сборки не добавляются:** X11 только через `dlopen`
  (`libX11.so.1`), хоткей не работает на Wayland/offscreen — там только кнопка;
  фоллбэк «терминал+stdin» покрывает headless (аддон шлёт HTML в stdin).
