# MyTetra — механизм обмена ветками: публикация, подписка, импорт

> Документ: `06_shared_branch_exchange.md`
> Статус: черновик дизайна. Концепция — в `05_design_proposal.md`.

## 1. Область действия

Этот документ детализирует механизм обмена ветками между участниками команды:
структуру каталога `shared/`, формат метаданных, использование внешнего `git`,
алгоритмы разности и выборочного импорта, политику безопасности и развёртывание.

## 2. Каталог обмена `shared/`

### 2.1 Размещение

- **По умолчанию** `<каталог бинарника>/shared` (как запрошено: «на том же
  уровне, где бинарник»).
- Ключ конфига `shareddir` (`conf.ini`) для переопределения.
- Если каталог бинарника недоступен для записи (установка в `/usr/local/bin`
  и т. п.) — фоллбэк `<рабочий каталог>/shared` с заметным уведомлением.
- При переносном (portable) запуске — `<каталог бинарника>/shared` рядом с
  `data/` и `trash/`.

Каталог `shared/` разделён на три структурные зоны:

- `shared/sync/` — **область данных**; единственная, что публикуется в
  Syncthing (общая папка Syncthing указывается именно на неё);
- `shared/local/` — **авторитетная зона владельца**; здесь собираются и хранятся
  публикации до выкладки в `sync/`. Не синхронизируется, в Syncthing не
  включается. Дубль 2x принят как меньшее зло (решение: copy-changed, не `mv` —
  `mv` теряет авторитет без git и не убирает swap-окно в `sync/`);
- `shared/.tmp/` — сборка версий и `.rev-*` бэкапы; вне `sync/`, на той же
  файловой системе (для `rename`);
- `shared/.git/` — **единый локальный репозиторий** истории всех публикаций
  (всех владельцев и веток). Он лежит над `sync/`/`local/`, в Syncthing не включается и
  самой репликацией никогда не трогается — повреждение git-метаданных
  синхронизацией исключено архитектурно (см. ADR-015, ADR-016).

Подписчик видит «что прилетело» по **данным** в `sync/` (изменились
`branch.xml`, `records/`, вырос `meta.json.publishVersion`), а не по
git-истории (см. раздел 6).

### 2.2 Структура `shared/`

```
shared/                          # каталог обмена (по умолчанию рядом с бинарником)
├── .git/                        # ЕДИНЫЙ репозиторий истории (все владельцы, все ветки)
│                                #   НЕ синхронизируется: лежит над sync/, Syncthing его не видит
├── local/                       # АВТОРИТЕТ владельца (НЕ синхронизируется, 2x дубль)
│   ├── <ownerId>_<ownerName>/   # собранные публикации до выкладки в sync/
│   │   └── <branchId>_<name>/
│   │       ├── branch.xml / records/ / meta.json / manifest.json / changelog.json
├── .tmp/                        # сборка версий и .rev-бэкапы (вне sync/)
├── sync/                        # ← ОБЩАЯ ПАПКА Syncthing (только она)
│   ├── <ownerId>_<ownerName>/   # зеркало local/ (copy-changed promotion, manifest последним)
│   │   └── <branchId>_<name>/   # каталог публикации одной ветки
│   │       ├── branch.xml       # фрагмент ветки (синтаксис mytetra.xml), актуальный срез
│   │       ├── records/         # копии записей
│   │       │   ├── <recordDir>/text.html
│   │       │   ├── <recordDir>/image<id>.png
│   │       │   └── <recordDir>/<attachId>.<ext>
│   │       ├── meta.json        # метаданные публикации (владелец, publishVersion)
│   │       ├── changelog.json   # append-only история версий (v, at, изменения)
│   │       └── manifest.json    # завершающий маркер версии (путь→sha256; пишется последним)
│   ├── <branchId3>_<name3>/     # фоллбэк: профиль владельца не настроен (плоская схема)
│   └── README.md                # (опционально) пояснение для людей/инструментов
```

Правила:

- каталог владельца: `<ownerId>_<ownerName>` (имя — санитизированное значение
  из профиля); **машинный ключ владельца — часть `ownerId` до первого `_`**;
  часть с именем фиксируется при первой публикации владельца и при
  переименовании в профиле **не меняется**;
- имя каталога публикации: `<branchId>_<имя ветки>` (имя — санитизированное
  название ветки, для читаемости в проводнике и Syncthing); **машинный ключ
  публикации — часть `branchId` до первого `_`**; переименование/пересоздание
  каталога запрещено; часть с именем фиксируется при первой публикации и при
  переименовании ветки **не меняется** (актуальный заголовок всегда в
  `meta.json.title`);
- если профиль не настроен (нет имени/id) — публикация идёт в плоскую
  `sync/<branchId>_<name>/` без каталога владельца; после настройки профиля
  владелец публикует в свой каталог владельца (подписки на старые — по
  `branchId`, пути фиксируются в индексе подписок);
- `meta.json` пишет только владелец; общих записываемых файлов нет. Внутри
  каждой публикации есть служебный `manifest.json` — завершающий маркер
  версии (также пишет владелец, последним);
- **git-история — единый репозиторий `shared/.git`**, один на все ветки и всех
  пользователей; внутри публикаций git-каталогов нет. Это **локальный журнал
  состояний** каждой машины: владелец коммитит при публикации/обновлении,
  подписчик — «снимок прилёта» при обнаружении изменений в `sync/`. В Syncthing
  не участвует;
- владелец пишет только в `sync/<свой каталог владельца>/`; история —
  `shared/.git`.
- для diff/импорта git **не обязателен**: базовое состояние подписчик держит
  как манифест диджестов (раздел 6); git — подстраховка (журнал, восстановление
  утраченного манифеста).

### 2.3 `meta.json` (схема)

```json
{
  "schemaVersion": 1,
  "branchId": "1789240589rc88x8v18d",
  "title": "База знаний по проекту",
  "ownerId": "U1789241111aaaa...",
  "ownerName": "Иван Петров",
  "ownerEmail": "ivan@example.com",
  "publishVersion": 7,
  "publishedAt": "2026-09-12T12:00:00Z",
  "encryptedSource": false,
  "notes": "Например, лицензия или условия использования"
}
```

- `ownerName`/`ownerEmail` берутся из профиля команды (`TeamProfile`) и
  соответствуют git-идентичности (см. раздел 5).
- `encryptedSource: true` — означает, что на стороне владельца ветка была
  зашифрована, а публикация отдана в расширенной форме (требует явного
  согласия владельца при публикации).

### 2.4 `branch.xml` — фрагмент ветки

Это **сам узел `<node>`** (с поддеревом) в синтаксисе и DTD `mytetra.xml`:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE mytetradoc>
<branch>
 <node id="1789240589rc88x8v18d" name="База знаний по проекту">
  <recordtable>
   <record id="..." name="..." author="" url="" tags="" ctime="..."
           dir="..." file="text.html"/>
  </recordtable>
  <node ...>...</node>
 </node>
</branch>
```

- Генерируется штатной сериализацией ветки (`KnowTreeModel::parseTreeToStreamWriter`
  и `recordtableExportDataToStreamWriter`), т. е. формат гарантированно совместим.
- Каталоги записей копируются в `records/` целиком.
- Имена файлов в `branch.xml` (`dir`, `file`, вложения) совпадают с путями
  внутри `records/` — фрагмент однозначно привязан к копии записей.
- Сериализация каноническая (`QXmlStreamWriter` с сортированными атрибутами):
  `QDomDocument::toString()` для этого не годится — порядок атрибутов в QDom
  случаен для каждого запуска процесса, и без каноникализации каждая сборка
  давала пустую версию публикации (рост журнала, вечные «обновления»).

### 2.5 `changelog.json` — история версий (синхронизируется)

Append-only лог, пишется владельцем при каждой публикации (дифф `local-old`
vs `local-new` через `BranchDiffEngine`), едет в `sync/` вместе с версией:

```json
{"schemaVersion":1,"entries":[
  {"v":7,"at":"2026-09-12T12:00:00Z","owner":"Иван",
   "changes":[{"kind":"update","recordId":"...","title":"...","fields":["name"],"text":true},
              {"kind":"add","recordId":"...","title":"..."}]}]}
```

Назначение: вкладка «История» в диалоге изменений + фильтр по записи.
Старого контента версий не хранит (только факты) — полный текст «было/стало»
подписчик смотрит парой «моя локальная копия → HEAD» (кнопка «Сравнить тексты»).
Контентная история при нужде доступна через локальный `shared/.git`
(`git show`), но не является базой.

## 3. Публикация (владелец)

Поток публикации (ADR-016, авторитет `local/` + copy-changed promotion):

1. UI: «Опубликовать в общую папку…» на ветке дерева;
2. проверки:
   - ветка не вложена в уже опубликованную;
   - `shareddir` доступен и настроен;
   - `git` найден в PATH (иначе понятная подсказка по установке; без git
     данные пишутся, журнал/восстановление отключены);
   - шифрованная ветка → предупреждение «публикация в расширенном виде» и
     подтверждение;
3. `BranchPublisher`:
   - сборка новой версии в `shared/.tmp/<uuid>/` (вне `sync/`, та же файловая
     система): `branch.xml` + `records/` (переиспользование экспорта с
     расшифровкой при необходимости) + `meta.json` (новый `publishVersion`);
   - atomic `rename` собранного в `local/<owner>/<branch>/` (старое — в `.tmp`
     бэкап, не в `sync/`); дописать `changelog.json` (дифф `local-old vs
     local-new` через `BranchDiffEngine`);
   - **коммит 1: только `local/<...>`**, сообщение `"<branchId> v<N>: <title>"`
     — source of truth, битым быть не может;
   - promotion `local/ -> sync/` методом copy-changed: сравнить манифесты
     (`путь→sha256`), скопировать новые/изменённые, удалить убранные,
     `manifest.json` и `changelog.json` — последними; каталог `sync/` на месте
     всё время (нет swap-окна «публикация исчезла»);
   - **коммит 2: только `sync/<...>`**, но только если
     `publicationVersionComplete(sync/, N)` — иначе не коммитить вообще
     (гард от битого коммита);
   - `git add -A` + commit идут раздельно по двум pathspec; `mv local -> sync`
     запрещён (теряет авторитет без git, фрагментирует историю, не убирает
     swap-окно);
4. лог в `ActionLogger`: `publishBranch` (добавить в белый список);
5. дальше — Syncthing разносит `sync/`.

### 3.1 Первичная публикация

Тот же поток §3, `publishVersion=1`. `git init` — единый `shared/.git`
(коммит 1 по pathspec `local/<...>`, коммит 2 по pathspec `sync/<...>`),
установка локальной идентичности (user.name/user.email из профиля).

### 3.2 Обновление публикации

Тот же поток §3: пересборка `branch.xml`, обновление изменённых записей в
`records/`, инкремент `publishVersion` в `meta.json`, дописка `changelog.json`,
затем promotion copy-changed в `sync/` — **последними** `manifest.json` и
`changelog.json`. Порядок важен: подписчик считает версию
полной только когда доехал и совпал именно `manifest.json` этой версии.
Убранные на стороне владельца записи **должны быть удалены и из `records/`**
(иначе подписчик не увидит удаление). Замена каталога целиком через
temp+rename запрещена (swap-окно «публикация исчезла» в `sync/`).

### 3.3 Обновление: вручную и автоматически

- Ручное «Обновить публикацию» — тот же путь, что §3.2, для текущей ветки.
  Проверка вложенности исключает собственный ключ ветки: иначе обновление уже
  опубликованной ветки всегда отклонялось бы как «вложенная публикация».
- Автоматически, без диалогов (`autoUpdatePublishedBranches`, только свои
  публикации по `ownerId`):
  - при сохранении дерева (`saveKnowTree`) — немедленно;
  - при сохранении текста записей (дерево не пересохраняется) — отложенно,
    debounce 5 с (`schedulePublicationsAutoUpdate` из `saveTextarea`), чтобы
    частые переключения записей не запускали экспорт и сверку дайджестов
    на каждое сохранение.
- Пустые обновления (контент не менялся) версию не трогают и коммит не создают.

## 4. Выбор инструмента версионирования: почему внешний `git`

### 4.1 Требования к инструменту

1. Хранить историю состояний публикации (кто, когда, что).
2. Давать «что изменилось между двумя состояниями» на уровне файлов.
3. Иметь автора (атрибуция) и возможность подписать изменения.
4. Быть локальным (никакого сервера) и корректно реплицироваться Syncthing.
5. Не требовать экспертных знаний от пользователя (UI скрывает детали).
6. Известный, надёжный, воспроизводимый на Linux/Windows/macOS.

### 4.2 Сравнение

| Вариант | История | Диффы | Авторство | Репликация Syncthing | Сложность встраивания | Вердикт |
|---------|---------|-------|-----------|----------------------|------------------------|---------|
| **Внешний `git`** (per-branch repo) | полная, компактная (объекты) | файловые диффы + `--stat` | user.name/email | отлично: только владелец пишет | средняя: `GitWrapper` через `CommandRunner`; новый внешний зависимость в runtime | **выбрано** |
| Внутренний журнал + манифесты (sidecar) | надо писать самим | надо писать самим | надо писать самим | ок (append-only) | высокая: дублирование git | отказ |
| Снапшоты-каталоги (`<branch>@<ts>/`) | нет, только копии | сравнение каталогов вручную | нет | расточительно (дубли данных) | средняя | отказ |
| Syncthing-версионирование (`stversions`) | только «откатить файл», мусор в истории | нет семантики | нет | не предполагает версионный анализ | низкая | не подходит |

### 4.3 Почему `git` подходит (и что закрыть)

- **Хранилище версий и файловые диффы — бесплатно и надёжно.** Семантику
  нашего формата git не знает и не должен: её даёт `BranchDiffEngine` (раздел 6).
- **Не требует сервера.** Единый репозиторий живёт в `shared/.git`. Syncthing
  реплицирует только `sync/`, поэтому git-история **никогда не синхронизируется**
  и не может быть повреждена репликацией. История — локальный журнал состояний
  каждой конкретной машины.
- **Единственный писатель** на репозиторий — само приложение на этой машине:
  владелец коммитит публикации/обновления, подписчик коммитит «снимки прилёта».
  Локальные репозитории разных машин не пересекаются → гонок в `.git` нет.
- **Идентичность** (`user.name`/`user.email`) = имя владельца из профиля.
  Для подписчика «кто изменил» берётся не из коммитов (их у него нет), а из
  `meta.json` (`ownerName`, `publishVersion`, `publishedAt`).
- Ограничение: ветка-публикация без сети у владельца — работает (коммит
  локальный, разнесётся позже через `sync/`).

### 4.4 Минусы git и меры

- **Внешняя зависимость.** MyTetra — Qt-only; git вызывается только во время
  работы через `CommandRunner`. **Дифф, импорт и детект обновлений работают
  без git** (на манифесте диджестов, см. раздел 6). Git нужен только для
  локального журнала и вторичного восстановления; первичное восстановление
  `sync/` у владельца — из `local/` без git. Без git журнал/вторичное
  восстановление отключаются с понятной подсказкой. Чтение `changelog.json`
  (история версий) работает без git — файл едет в `sync/`.
- **Бинарные файлы растят `.git`.** Меры: предупреждение о размере, кнопка
  «Архивировать историю» (обновить baseline + сбросить/GC локальный журнал с
  согласия пользователя), `.gitattributes` с `-delta` для бинарных расширений.
- **Чувствительность к конфликтам lock-файлов.** Исключена архитектурно:
  `.git` вне Syncthing, на каждой машине пишет только само приложение и строго
  последовательно (коммит — атомарно, temp+rename).
- **Поведение на Android.** `git` может отсутствовать → журнал/восстановление
  показывают подсказку; подписки, срез, diff и импорт продолжают работать.

### 4.5 Восстановление `sync/` (local первично, журнал вторично)

Единый репозиторий `shared/.git` — журнал и **вторичный источник
восстановления**; первичный у владельца — `shared/local/`:

- дисциплина коммитов публикации (ADR-016): **коммит 1 только
  `local/<owner>/<branch>`** (`"<branchId> v<N>: <title>"`, source of truth),
  затем promotion copy-changed в `sync/`, затем **коммит 2 только
  `sync/<owner>/<branch>`** (`"mirror <branchId> v<N>"`) и только при
  `publicationVersionComplete(sync/, N)` — битое в журнал не попадает;
  `mv local -> sync` запрещён;

- при каждом фактическом изменении `sync/` (публикация/обновление владельца,
  «прилёт» у подписчика) `SharedDirWatcher` после устаканивания изменений
  (debounce + две подряд одинаковые сигнатуры) коммитит текущее дерево `sync/`
  («snapshot N»); коммит создаётся только если область реально изменилась
  (`git diff --cached --quiet` — пустые снимки не делаем). Снимок пишется
  **только когда в `sync/` есть хотя бы одна целостная публикация** (весь
  манифест версии совпадает) — журнал хранит только последние доехавшие
  состояния, частичные переносы Syncthing в него не попадают;
- **легитимные изменения приложения** (публикация/обновление/отзыв
  публикации, авто-обновление своих веток) фиксируются в журнале **немедленно**
  (`requestImmediateSnapshot`, без debounce — данные записаны самим
  приложением, «частичных» состояний нет). Отзыв последней публикации
  разрешено фиксировать как переход к пустой `sync/`, поэтому осознанное
  удаление не воспринимается как потеря данных и не предлагает восстановление;
- если `sync/` повреждена или удалена — восстановление предлагается в порядке:
  1. **из `local/`** (быстрый перепромоут по манифесту, без git; только свои
     публикации владельца);
  2. из журнала (`git -C shared/.git checkout -f HEAD -- sync/` целиком либо
     только отсутствующие публикации) — при обновлении состояния приложение
   один раз за сессию предлагает восстановление (`isRecoveryAvailable`).
  Действия также доступны в контекстном меню панели подписок («Restore sync/
  from local…», «Restore sync/ from journal…», «Archive journal
  history…»);
- журнал хранит и отозванные/удалённые из `sync/` публикации — до ближайшего
  снимка: после отзыва приложение немедленно фиксирует новое состояние, а
  прежнее остаётся в истории журнала до «Архивировать историю» (текущее
  состояние становится новым корнем журнала (`git checkout --orphan` +
  `branch -M`), прежние снимки удаляются (`reflog expire --all`,
  `gc --prune=now`));
- **ограничение:** журнал локальный — он покрывает порчу/удаление `sync/` на
  этой машине; потеря всего `shared/` (включая `.git`) лечится только внешним
  бэкапом, о чём говорится в пользовательской документации;
- без git восстановление недоступно; diff/импорт продолжают работать по диджестам
  (см. 6.3 и 7.4).

*Реализовано (коммит Фазы 7.3):* `GitWrapper::commitIfChanged/checkoutFromRef/
listFilesInRef/currentBranchName/archiveHistory`, снимки в `SharedDirWatcher`
(только целостные состояния, guard пустых коммитов), авто-предложение и
контекстное меню восстановления/архива.

## 5. Идентичность и имя владельца

- Профиль команды в `conf.ini`: `teamname`, `teamemail` (+ при необходимости
  `teamid`). Редактируется на странице «Команда» настроек.
- При публикации из профиля берутся: `ownerName`, `ownerEmail` (в `meta.json`)
  и git-идентичность (`git -C shared/<ownerDir>/<branchId>_<name> config user.name/email`),
  где `<ownerDir>` — каталог владельца (при пустом профиле — плоский путь).
- `ownerId` — отдельное от веток пространство ID узла (`U<UniqueId>`), создаётся
  лениво при первой публикации и хранится в профиле. `ownerId` — также машинный
  ключ каталога владельца (`ownerId` в имени `<ownerId>_<ownerName>` до первого `_`).
- Подписчик видит имя владельца в: метке подписки в панели «Подписки»
  («Название — Имя»), деталях изменения, тултипе, индексе подписок.
- Владелец видит свои опубликованные ветки в дереве разделов по бейджу «рука»
  (значок как у SMB); свои публикации в списке «Доступно» не показываются.

### 5.1 UI подписок: панель в левой колонке (дизайн-решение)

Модель базы не трогается (корень в `mytetra.xml` один). Вместо виртуальных
узлов в дереве используется **панель «Подписки»** — `QTreeWidget` в левой
колонке под деревом разделов (вертикальный `QSplitter`):

- группа **«Подписки»** — оформленные подписки: `Название — Имя Владельца`;
  при доступных обновлениях (`publishVersion`/диджесты отличаются от
  сохранённого снимка или ни разу не просмотрено) — бейдж «*» и жирный шрифт;
- группа **«Доступно»** — найденные в `sync/` публикации без подписки
  (свои не показываются);
- контекстное меню подписки: «Подписаться» / «Отписаться»,
  «Отметить как просмотренное» (базовая точка → HEAD), «Открыть срез...»
  (Фаза 3.5), «Обновить список»;
- подписка («Подписаться») сразу выполняет первый импорт: срез публикации
  целиком создаётся в основной БД (`imported/<owner>/<title>`), базовая точка
  выравнивается; последующие обновления забираются вручную через
  «Show changes / Import...»;
- открытие среза (`BranchSliceDialog`, только чтение): дерево веток/записей
  по `branch.xml`, текст записи из `records/<dir>/<file>`; срез подсвечивает
  изменения с базовой точки подписки (новые — зелёным, изменённые — синим,
  удалённые владельцем — красная секция «Удалено владельцем» с плейсхолдерами
  веток и записей); вызывается по
  двойному клику/Enter или из контекстного меню подписки через сигнал
  `openSliceRequested(branchId, publicationDir)`;
- обновление панели: по `SharedDirWatcher::sharedDirChanged`,
  `SubscriptionRegistry::subscriptionsChanged` и `teamProfileChanged`;
- штатные действия публикации/обновления/отзыва ветки — по-прежнему
  в контекстном меню дерева; владелец видит свои опубликованные ветки
  по бейджу «рука» (`PublishedBadgeDelegate`, иконка
  `:/resource/pic/branch_published.svg`).

## 6. «Что изменилось»: семантическая разность

### 6.1 Построение разности между baseline и HEAD

Единая схема, **не зависящая от синхронизированного git**:

1. **База состояния подписчика** — манифест-снимок, хранящийся в
   `subscriptions.ini` (поле `baselineSnapshot`):
   - сериализованный `branch.xml` среза публикации на момент последнего
     просмотра/импорта;
   - карта `recordId → sha256` содержимого `records/<dir>/<file>` на тот же
     момент.
   Никаких старых файлов не держим — только тексты полей и хеши содержимого.
2. **Детект обновления (дешёвый, для панели)**: `meta.json.publishVersion`
   изменился относительно сохранённого `baselinePublishVersion` → «*».
   Если манифест актуальной версии `manifest.json` ещё не доехал/не совпал по
   заголовку — «…» и подсказка «обновление в пути» (без прохода по файлам).
3. **Готовность версии (для диффа/импорта)**: дифф строится только по
   целостной версии. `manifest.json` — завершающий маркер: `путь→sha256`
   всех файлов данных, пишется владельцем последним. Целостность проверяется
   в момент чтения публикации (и отдельно для каждой записи перед импортом) —
   без отдельного полного прохода, тексты и так читаются для хешей HEAD.
   Частично доехавшая публикация недоступна для диффа — UI показывает
   «ожидание данных» с повторными проверками статуса; взять её за baseline
   (подписаться / «отметить просмотренным») нельзя.
4. **HEAD-срез** читается из актуальных файлов `sync/<owner>/<branch>/`
   (`branch.xml` + содержимое `records/`).
5. `BranchDiffEngine` парсит оба фрагмента (HEAD — из файлов `sync/`,
   baseline — из манифест-снимка) и строит список изменений (таблица ниже).
   Для `textSha` у baseline-фрагмента используются сохранённые хеши; для
   HEAD — чтение файлов из `sync/`.

| Тип | Родственность | Опасность |
|-----|---------------|-----------|
| `branch.props` | изменены поля/название ветки | нормально |
| `branch.move` / `branch.add` / `branch.delete` | структура поддерева | delete — опасно |
| `record.add` | новый id записи | нормально |
| `record.fields` | изменены name/author/url/tags | нормально |
| `record.text` | изменён hash `text.html` (или файл списка) | нормально |
| `record.attach` | изменён набор `<files>` | нормально |
| `record.delete` | id исчез из фрагмента | **опасно** |

### 6.2 Изменение записи: признак

- Сравнение «натуральных» полей записи (кроме `ctime`, `id`, `dir`, `file`);
- содержимое: sha256 текущего файла `records/<dir>/text.html` сравнивается с
  хешем из baseline-манифеста; при несовпадении файл помечается изменённым.

### 6.3 Git как подстраховка и восстановление

- Единый `shared/.git` на каждой машине — локальный журнал состояний; при
  каждом фактическом изменении `sync/` приложение коммитит целостное дерево
  `sync/` («snapshot N», см. 4.5); пустые снимки не создаются.
- **Восстановление**: если `sync/` повреждена или удалена, приложение
  предлагает восстановить из последнего снимка (см. 4.5).
- **Если git отсутствует**: diff, импорт и детект обновлений продолжают
  работать по диджестам; журнал/восстановление — недоступны.

### 6.4 Представление подписчику

Список с чекбоксами:

- по умолчанию выбраны: `record.add`, `record.fields`, `record.text`,
  `record.attach`, `branch.props`;
- **не выбраны и требуют явного согласия**: `record.delete`, `branch.delete`;
- у каждого пункта: заголовок (имя записи/ветки), краткое описание, размер
  изменения, детали: для полей — таблица старое/новое, для текста —
  построчный diff (локальная копия → версия владельца, `TextDiff`, Qt-only
  Myers); картинки в тексте — строками `[изображение: …]`, вложения —
  списками добавленных/удалённых (бинарное содержимое не сравнивается).
- таблица раскрашена: новое — зелёное, изменённое — синее, удаление — красное;
  отдельная колонка `Diff` отмечает строки с построчным diff; детали diff
  показываются внизу (панель ×2 высоты) и по кнопке / двойному клику —
  в отдельном   окне (`TextDiffDialog`): тройной вид — слева построчный diff, справа два
  столбца полного рендера «Было / Стало» (картинки грузятся относительно
  каталогов записей).

## 7. Импорт (выборочный, ручной)

### 7.1 Индекс подписок (`subscriptions.ini`)

Секция на ветку (`branchId` → параметры):
`sharedPath` (включает каталог владельца в `sync/`),
`ownerName`, `publishVersion`, `baselineSnapshot` (сериализованный
`branch.xml` + карта `recordId → sha256` текстов записей на момент
последнего просмотра/импорта),
`localTargetBranchId`,
`records{ sharedRecordId → { localRecordId, snapshotHash } }`.

`baselineSnapshot` заменяет прежний `baselineCommit`: снимок вместо
git-хеша; git теперь только локальная подстраховка (раздел 6.3).

### 7.2 Применение выбранных изменений

`SubscriptionImportEngine`:

1. **Создание записи**: через штатный путь создания записи (новые локальные
   `id`/`dir`); файлы копируются из `sync/<ownerDir>/<branchId>_<name>/records/<dir>/` в
   `data/base/<newDir>/`; карта `sharedRecordId → localRecordId` сохраняется.
2. **Замена записи**:
   - найти локальную запись по карте;
   - сравнить `snapshotHash` (хеш, сохранённый при прошлом импорте) с текущим
содержимым локальной записи: если **изменился** (локальная правка) →
      конфликт: диалог «заменить / сохранить обе» (локальная правка получает
      суффикс `_conflict-<дата>`, импортируется версия владельца, карта
      переносится на новую копию);
   - иначе обновить поля и заменить файлы (атомарно, старые файлы — в корзину).
3. **Удаление записи**:
   - только явно отмеченный пункт;
   - перед удалением локальная запись переносится **в корзину подписчика**
     (штатный `removeDirectoryToTrash`), затем запись убирается из
     `recordtable` и `mytetra.xml` сохраняется.
4. **Целевая зона** (решение): первый импорт — всегда полное поддерево
   в `imported/<ownerName>/<branchId>_<имя>/`; последующие обновления — в
   эту же копию (карта веток `branchesMap`), см. раздел 7.5. Каждое изменение
   маршрутизируется в таблицу своей ветки-копии (`change.branchId` →
   `branchesMap`); корень копии — только фолбэк. Записи из ещё
   не импортированных новых подветок создаются в корневой копии
   (структурный импорт — следующие этапы).
5. По завершении: `baselineSnapshot = текущий снимок` (фрагмент + sha256 текстов
   записей), `publishVersion = meta.publishVersion`; метка импортированных
   записей «из публикации <ownerName>» в `tags` **не проставляется
   автоматически** (решение отложено — не менять пользовательские данные без
   согласия).

### 7.3 Запрет авто-импорта

Автоматический импорт изменений публикации в БД **не выполняется никогда**.
Единственные автоматические действия — уведомление о доступных изменениях и
витрина в UI. Импорт — кнопка «Применить выбранное» + подтверждения для
опасных пунктов.

### 7.4 Решения Фазы 4 (по реализации)

- **Режимы импорта.** В диалоге «Что изменилось» селектор режима —
  фильтр над списком изменений: «выборочно (вручную)» (по умолчанию),
  «только новые» (новые записи + новые ветки), «всё, кроме удалений»,
  «всё, включая удаления». Смена режима переотмечает чекбоксы применимых
  изменений; ручная правка любого чекбокса возвращает режим к «выборочно».
  Применение удалений всегда подтверждается диалогом.
- **Импорт структуры дерева.** Изменения `branch.add/rename/move/delete`
  применяются в локальную копию: создание (под ближайшим отображённым
  предком), переименование, перемещение (`KnowTreeModel::moveBranchToParent`
  с защитой от циклов), удаление через штатный путь модели (файлы записей —
  в корзину, карты подписки чистятся). Корень подписки не удаляется никогда.
  Порядок применения — порядок строк диалога (ветки раньше записей).
- **Продвижение baseline и остаточный diff.** Диалог и срез показывают не
  свежий дифф baseline→HEAD, а остаточный: минус изменения, уже отражённые
  в локальной копии (сверка живого состояния с HEAD), минус применённые
  удаления (`appliedDeletes` в `subscriptions.ini` — связь и локальный объект
  после удаления исчезают, иначе дифф показывал бы удаление вечно).
  После полного импорта список пуст, после частичного — только остаток.
  Базовая точка подтягивается к текущему снимку, когда применены **все**
  показанные изменения, либо кнопкой «Отметить просмотренным» (тогда
  `appliedDeletes` чистится). Живой текст читается напрямую из файлов
  без побочных эффектов (без диалогов и создания заготовок).
- **Идемпотентность.** Повторное применение уже импортированного изменения
  не создаёт дубликат: наличие связи в карте маршрутизирует запись в ветку
  «замена», неизменённый локальный снапшот перезаписывается без потерь.
- **Целевая зона импорта** — см. 7.2 п.4 (первый импорт — полное поддерево в
  `imported/<ownerName>/<branchId>_<имя>/`, обновления — в эту копию через
  карту веток `branchesMap`).

## 8. Безопасность и приватность

- В `sync/` уходят только те данные, которые владелец явно опубликовал.
- Шифрованная ветка публикуется расшифрованной только с явного согласия
  владельца (аналог штатного экспорта). Публикация «как есть» зашифрованного
  содержимого — не поддерживается (подписчики не смогут прочитать/диффачить).
- Личные БД участников вне репликации; `shared/` не содержит ссылок на
  локальные пути.
- `meta.json` — только публичная информация (имя, email). Предупреждать
  владельца об этом при публикации.

## 9. .stignore / синхронизация Syncthing

Общая папка Syncthing — **только `shared/sync/`**. Единый локальный журнал
`shared/.git/`, авторитет `shared/local/` и сборка `shared/.tmp/` лежат рядом
с `sync/` и в Syncthing не включаются; переносной
каталог бинарника (`data/`, `trash/`) — тоже вне синхронизации.

Файл `shared/sync/.stignore` **генерируется кодом** при старте слежения
(`SharedDirWatcher::ensureSharedDirExists`), чтобы Syncthing не тянул
промежуточный churn promotion (copy-changed пишет файлы по одному):

```
// временные файлы записи и promotion
*.part
*.tmp
.~lock.*
.tmp-*
*.rev-*
```

Восстановление: у владельца первично — из `local/` (быстрый перепромоут по
манифесту, без git), вторично — из `.git`; у подписчика `local/` чужого нет —
только его локальные snapshot'ы `sync/` в его `.git` + `manifest`-гард.

Конфликтные копии Syncthing (`*.sync-conflict-*`, включая каталоги-копии
целиком) специально игнорируются везде: не попадают в манифест, не видны
как публикации в списках и поиске, promotion их не удаляет. Разруливает
конфликты человек в файловом менеджере; подписчик их не видит
(целостность версий — только по манифесту).

Если участник настраивает общую папку на **родительский** каталог (например,
весь каталог бинарника), для этой папки действуют прежние правила исключений:

```
// не делиться личными БД, корзиной и локальным журналом истории
.git/
data/
trash/
database.ini
// журналы/конфиги приложения
conf.ini
knownbases.ini
subscriptions.ini
actionLog.txt
actionLogPrev.txt
```

Для чистой настройки рекомендуем: **одна папка Syncthing = `shared/sync/`**.
Пошаговое руководство для людей — в [syncthing-setup.md](syncthing-setup.md).

## 10. Развёртывание и тестирование

- Использовать существующий `CommandRunner` для git (`runSimple` синхронный
  вариант есть), атомарные записи — temp+rename.
- Тестовый полигон: два рабочих каталога MyTetra, каждый со своим каталогом
  `shared/` (свой `shared/.git`); общая папка Syncthing = `shared/sync/`;
  эмуляция Syncthing скриптом (копирование изменений + создание
  `.sync-conflict-*`), затем живой Syncthing.
- Автотесты: парсер фрагментов, `BranchDiffEngine` (пары baseline-снимок/HEAD →
  ожидаемый список изменений), `SubscriptionImportEngine` (добавить/заменить/
  удалить/конфликт), `GitWrapper` на фиктивном репозитории, восстановление
  `sync/` из журнала.
- Перф: публикация ветки 1000 записей — целевые замеры; `git gc`/«Архивировать
  историю» по кнопке.

## 11. Контрольные сценарии (проверка дизайна)

| Сценарий | Ожидание |
|----------|----------|
| Владелец обновил запись | подписчик видит «изменена запись N», выбирает, импортирует |
