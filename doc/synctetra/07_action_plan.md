# MyTetra — план действий: подписочная модель и обмен ветками через Syncthing (v2)

> Документ: `07_action_plan.md`
> Статус: **черновик** — план для подписочной модели (local-first).
> Концепция: `05_design_proposal.md`; детали обмена: `06_shared_branch_exchange.md`.

## Целевой результат

MyTetra умеет: владелец публикует ветку в каталог `shared/` (рядом с
бинарником, путь настраивается); каталог реплицируется Syncthing; участники
подписываются на ветку (read-only, с именем владельца); при обновлениях
владельца видят **список изменений** и **вручную выборочно** импортируют их в
свою личную БД. Никакого автоимпорта; никаких изменений формата БД.

## Принцип планирования

Фазы независимо вливаются в `experimental`. Каждая фаза — самостоятельная
ценность. Фазы 1–3 — фундамент; 4–5 — функциональность; 6 — стабильность.

## Фаза 1. Профиль команды и каталог обмена

**Цель:** у приложения появляется идентичность участника и настраиваемый путь
обмена; БД не трогается.

Задачи:

- [x] 1.1 Ключи `conf.ini`: `shareddir`, `teamname`, `teamemail`, `teamid`
      (регистрация в таблицах параметров `AppConfig`.
- [x] 1.2 `TeamProfile` — чтение/сохранение профиля; ленивое создание
      `teamid` (пространство `U<...>`, отдельное от веток/записей).
- [x] 1.3 Разрешение `shareddir`: по умолчанию `<каталог бинарника>/shared`;
      если каталог бинарника не писабелен — фоллбэк `<рабочий каталог>/shared`
      с уведомлением.
- [x] 1.4 Страница настроек «Команда» (в `views/appConfigWindow/`): имя, email,
      путь обмена, кнопка «создать ID».
- [x] 1.5 `SharedDirWatcher`: `QFileSystemWatcher` на `shareddir` + страховочный
      таймер (переиспользовать `TimerMonitoring`); сигнал «изменился shareddir».
- [x] 1.6 `GitWrapper` — вызов внешнего `git` через `CommandRunner`
      (`runSimple`, `runSimpleAndGetOutput`): `init`, `config user.*`, `add`,
      `commit`, `log`, `diff`, `rev-parse HEAD`, `cat-file`/`show`. Проверка
      наличия git в PATH. Закрывает Фазу 1.

Приёмка: профиль и путь сохраняются; watcher сообщает о появлении/исчезновении
подкаталогов в `shared/`; GitWrapper умеет инициализировать репозиторий,
коммитить и отдавать `HEAD`/`log`; БД и старые функции синхронизации не затронуты.

## Фаза 2. Публикация (сторона владельца)

**Цель:** ветка экспортируется в `shared/<ownerId>_<ownerName>/<branchId>_<name>/`
(при пустом профиле — в плоской `shared/<branchId>_<name>/`) с метаданными
владельца и git-историей.

Задачи:

- [x] 2.1 `BranchPublisher`:
      - путь публикации `shared/<ownerId>_<ownerName>/<branchId>_<name>/`
        (санитизация имени ветки; ключ ветки — часть `branchId` до первого `_`,
        ключ владельца — часть `ownerId` до первого `_`; при пустом профиле —
        без каталога владельца);
      - сборка `branch.xml` (переиспользовать сериализацию дерева
        `KnowTreeModel::parseTreeToStreamWriter` /
        `recordtableExportDataToStreamWriter`);
      - копирование `records/<dir>/*` из каталогов записей (расшифровка при
        необходимости — по образцу `exportRelatedDataAndDecryptIfNeed`);
      - `meta.json` (схема из `06`, раздел 2.3);
      - публикация/обновление: техника temp+rename в пределах каталога,
        затем `git add -A` + commit; инкремент `publishVersion`.
- [x] 2.2 UI в контекст-меню дерева: «Опубликовать в общую папку…»
      (точка входа уже добавлена в Фазе 1, основной функционал здесь),
      «Обновить публикацию», «Отозвать публикацию» (удаление каталога +
      commit-фиксация удаления), статус-индикатор публикации ветки.
      Отзыв удаляет каталог публикации целиком в корзину, включая скрытый
      `.git` (`DiskHelper::removeDirectoryToTrash` с фильтром скрытых
      элементов), иначе публикация продолжала обнаруживаться.
- [x] 2.3 Проверки: вложенная публикация, шифрованная ветка (подтверждение
      расшифровки), вес вложений (предупреждение о росте `.git`).
- [x] 2.4 Лог действий: добавить в «белый список» `ActionLogger` события
      `publishBranch`, `updatePublication`, `revokePublication`.

Приёмка: публикация создаёт каталог `shared/<ownerId>_<ownerName>/<branchId>_<name>/`
(или плоский при пустом профиле), читаемый другими
экземплярами; повторная публикация создаёт новый коммит; уведомление владельцу
о расшифровке.

## Фаза 3. Подписки (сторона подписчика)

**Цель:** панель «Подписки» в левой колонке (без изменения формата БД);
подписка на чужие публикации; детект обновлений; затем read-only срез.

Задачи:

- [x] 3.1 `SubscriptionRegistry`: `<рабочий каталог>/subscriptions.ini`
      (по образцу `KnownBasesConfig`): секция на ветку, поля
      `sharedPath`, `ownerName`, `baselineCommit`, `localTargetBranchId`.
- [x] 3.2 Панель **«Подписки»** (виджет в левой колонке под деревом, дизайн-решение):
      - группы «Подписки» и «Доступно» (последняя — незаписанные публикации;
        свои публикации владелец видит по бейджу «рука» в дереве);
      - подписка/отписка/«отметить просмотренным» через контекстное меню;
      - отписка убирает запись из `subscriptions.ini`, данные не трогает;
      - двойной клик по подписке — запрос на открытие среза (Фаза 3.5);
      - бейдж «рука» на опубликованных ветках владельца в дереве
        (`PublishedBadgeDelegate`, набор ключей из `listPublishedBranchKeys`).
- [x] 3.3 Read-only enforcement: в панельном дизайне виртуальных узлов в
      дереве БД нет — данные среза существуют только в `shared/`; панель
      «Подписки» нередактируема (`NoEditTriggers`), диалог среза — строго
      только-чтение; контроллеры `RecordTableController`/`TreeScreen` работают
      только с личной БД и защитных веток не имеют.
- [x] 3.4 Детект обновлений: при обновлении панели (сигналы
      `SharedDirWatcher::sharedDirChanged`, `subscriptionsChanged`) — сравнение
      `HEAD` (`GitWrapper::getHead`) с `baselineCommit`; при отличии — подписка
      помечается бейджем «*» и жирным шрифтом.
- [x] 3.5 Просмотр среза: `BranchSliceDialog` — окно (только чтение) со
      списком записей по `branch.xml` и текстом из `records/<dir>/<file>`;
      открывается по двойному клику/«Открыть срез...» через сигнал
      `openSliceRequested(branchId, publicationDir)`.

Приёмка: подписка появляется в панели «Подписки» с именем владельца и не
редактируется; новые версии владельца помечаются бейджем; отписка не влияет
на данные в `shared/`.

## Фаза 4. «Что изменилось» и выборочный импорт

**Цель:** наглядная разница и безопасный ручной импорт.

> Примечание. Фазы 4–5 реализованы на подходе с per-branch `.git` внутри
> публикаций и `baselineCommit`. Фаза 7 (ADR-015) переносит данные в
> `shared/sync/` с единым локальным `shared/.git` и переводит diff на
> диджесты/`baselineSnapshot` — изложенное ниже фиксирует текущую
> реализацию, новый макет см. в `06` (§2, §4.5, §6).

Задачи:

- [x] 4.1 `BranchDiffEngine` (см. `06`, раздел 6): унифицированный парсер
      фрагментов; построение списка изменений `branch.props`, `record.add`,
      `record.fields`, `record.text`, `record.attach`, `record.delete`,
      `branch.move/delete`; опасность для delete; сравнение контента по sha256.
      *Реализовано:* `parseFragment` (XML → `FragmentData`), `fillTextShas`
      (контент из `shared/` для HEAD и `git show baseline:...` для базовой
      точки), `buildChangeList` (записи и ветки по id, поля старое/новое,
      привязка вложений по внутренним именам `<files>`).
- [x] 4.2 `ChangeViewDialog` (view): таблица изменений с чекбоксами; по
      умолчанию выбраны неопасные; delete — нет и требует подтверждения;
      панель деталей (поля старое/новое, содержимое), кнопка «Применить
      выбранное», «Отметить просмотренным» (обновление baseline).
      *Реализовано (+структура, ADR-018):* диалог возвращает действие
      и выбранные индексы; структурные изменения веток
      (`branch.add/move/delete/rename`) — с чекбоксами, применяются
      в локальную копию (создание/переименование/перемещение/удаление
      через корзину); `branch.delete` — опасное, по умолчанию не отмечено.
- [x] 4.3 `SubscriptionImportEngine` (см. `06`, раздел 7):
      - создание записи (новый локальный id/dir; копирование файлов; карта
        `sharedRecordId → localRecordId` в индексе);
      - замена с детектом локальной правки (сравнение снапшот-хеша) →
        диалог «заменить / сохранить обе»;
      - удаление только явно, через корзину подписчика (`DiskHelper::
        removeDirectoryToTrash`);
      - структура веток (`applyBranchAdd/Rename/Move/Delete`, ADR-018):
        создание под ближайшим отображённым предком, перемещение через
        `KnowTreeModel::moveBranchToParent` (защита от циклов), удаление
        штатным путём модели с чисткой карт подписки; корень не трогается;
      - обновление `baselineCommit`.
- [x] 4.4 Аудит: события импорта в `ActionLogger` (`importSubscriptionChanges`,
      `importConflictSolver` и т. п.).

Решения Фазы 4 (зафиксированы; структура — ADR-018):
- записи и структура веток (`branch.add/move/delete/rename`) импортируются
  в локальную копию; каждое изменение маршрутизируется в таблицу своей
  ветки-копии (корень — фолбэк);
- baseline продвигается к HEAD, только если применены ВСЕ применимые
  изменения; при частичном применении базовая точка остаётся на месте,
  чтобы непросмотренное продолжало отображаться; «Отметить просмотренным»
  продвигает baseline всегда;
- конфликт «сохранить обе»: локальная копия с локальной правкой получает
  суффикс `_conflict-<дата>`, импортируется версия владельца, карта
  `sharedRecordId → localRecordId` переносится на новую копию;
- метка импортированных записей в `tags` автоматически не проставляется
  (решение отложено — не менять пользовательские данные без явного согласия).

Приёмка: все сценарии UC-2..UC-5 из `04`; импорт идемпотентен; повторный
просмотр не показывает уже импортированное; удаления корректно защищены.

## Фаза 7. Новый макет каталога обмена и устойчивость к Syncthing
**Цель:** убрать git-метаданные из области репликации; развести область данных
и локальный журнал; обеспечить восстановление данных при порче/удалении
`sync/` (ADR-015).

Задачи:

- [x] 7.1 Макет `shared/sync/` + единый `shared/.git` (вместо per-branch `.git`
      внутри каталогов публикаций):
      - данные публикаций переезжают в `sync/<ownerId>_<ownerName>/<branchId>_<name>/`;
      - единый репозиторий `shared/.git` — локальный журнал состояний (все
        владельцы, все ветки); старые per-branch истории переносятся скриптом;
      - Syncthing: общая папка = `shared/sync/`.
      *Реализовано (коммит `1578294d`):* новые публикации создаются в `sync/`,
      журнал — общий `shared/.git` (коммит области `sync/` по pathspec); старые
      публикации с per-branch `.git` читаются/обновляются в своём макете;
      поиск/списки/`findRepositoryRoot` объединяют оба корня.
- [ ] 7.2 Diff/baseline по диджестам (без синхронизированного git):
      - `baselineSnapshot` в `subscriptions.ini`: сериализованный `branch.xml`
        среза + карта `recordId → sha256` текстов записей;
      - `SubscriptionImportEngine::changesSinceSnapshot` — сравнение актуальных
        файлов `sync/` со снимком (путь `git show baseline` в диффе не используется);
      - детект обновления — по `meta.json.publishVersion` (дешёвый) с
        проверкой целостности версии через `manifest.json`.
      *Реализовано:* манифест `manifest.json` (завершающий маркер версии) —
      построчный `путь→sha256`, пишется последним; детект в панели — по
      `publishVersion` + заголовку манифеста («*» и «…» при недоезде данных);
      дифф и импорт — только по целостной версии (сверка в момент чтения/
      применения, без отдельного полного прохода); при частичной доставке
      Syncthing — «ожидание данных» с повторными проверками статуса;
- [x] 7.3 Локальный журнал и восстановление:
      - коммит «snapshot N» дерева `sync/` при каждом фактическом изменении
        (guard от пустых коммитов — переиспользовать `publicationContentDigest`);
      - восстановление: `sync/` пуста/побита → предложить `git checkout
        <последний snapshot> -- sync/…` (весь каталог или только отсутствующие
        публикации);
      - «Архивировать историю» (обновление базовой точки + сброс/GC журнала с
        согласия пользователя).
      *Реализовано:* `SharedDirWatcher` делает снимок области `sync/` после
      устаканивания изменений (debounce + две подряд одинаковые сигнатуры),
      только при наличии целостных публикаций (disk-манифест версии совпадает)
      и только при фактическом изменении (`git diff --cached --quiet`;
      `GitWrapper::commitIfChanged`); авто-предложение восстановления при
      обнаружении пустой/битой `sync/` (раз за сессию, `isRecoveryAvailable`) +
      пункты «Restore sync/ from journal…» / «Archive journal history…» в
      контекстном меню панели подписок; восстановление целиком
      (`git checkout -f HEAD -- sync`) или только недостающих публикаций;
      архивирование истории (`git checkout --orphan` + `branch -M` +
      reflog expire + `gc --prune=now`).
- [x] 7.4 `GitWrapper`/`BranchPublisher`:
      - единый репозиторий: `git -C shared/.git` + относительные пути `sync/…`;
      - без git в PATH: дифф/импорт/детект продолжают работать (диджесты);
        журнал/восстановление — отключены с подсказкой.
      *Реализовано:* `GitWrapper::runGit` вызывает `git -C <repo>` с
      относительными путями (`sync`, `sync/<owner>/<branch>`); публикация без
      git завершается успешно (`Result::journalDisabled`, данные — branch.xml,
      records/, meta.json, manifest.json — записаны, снимок пропущен,
      `.git` не создаётся); предупреждение о росте истории показывается только
      при активном журнале; диалог успеха публикации и контекстное меню панели
      подписок содержат подсказку о недоступности журнала; отзыв и
      авто-обновление без git работают (снимки — no-op через гарды
      `isGitAvailable`). Попутно исправлено двойное хеширование в
      `changesSinceSnapshot` (в снимке лежат готовые sha256 — подставляются
      напрямую, иначе каждая сверка давала фантомные RecordText-изменения).
- [x] 7.5 Обратная совместимость: чтение старых публикаций (с `.git` внутри) —
      продолжает работать; новые пишутся в `sync/`.
      *Реализовано:* поиск/списки (`findPublicationDir`, `listPublications`,
      `listPublishedBranchKeys`) объединяют оба корня (`sync/` + плоский
      `shared/`); обновление legacy — на месте в per-branch `.git`, новые
      публикации — только в `sync/`; детект/дифф/импорт/срез legacy — по
      meta.json и файлам с диска (целостность legacy гарантирует `.git`,
      манифест не требуется); отзыв legacy — в корзину включая скрытый `.git`;
      журнал `sync/` legacy-публикации не покрывает (только область данных).
      Попутно: маркер «данные в пути» `(...)` больше не ставится legacy
      per-branch без манифеста (`isPublicationDataPending`: отсутствие
      манифеста при наличии `.git` — штатно, а не ожидание).
- [ ] 7.6 Тесты: эмуляция порчи/удаления `sync/` и восстановление из журнала;
      конкурентная публикация двух владельцев; «битый .git» не влияет на срез/
      diff/импорт.

Приёмка: общая папка Syncthing = `sync/`; повреждение/удаление `sync/`
восстанавливается из журнала; diff и импорт работают без установленного git.

## Фаза 8. Авторитет `local/`, promotion copy-changed, changelog (ADR-016)

**Цель:** экспорт вне опасной зоны; `sync/` — только зеркало; история версий
синхронизируется; битые состояния в журнал не попадают.

Задачи:

- [x] 8.1 Макет `shared/local/` + `shared/.tmp/`:
  сборка версий в `.tmp/<uuid>/`, atomic rename в `local/<owner>/<branch>/`;
  `.tmp` и `.rev-*` никогда внутри `sync/`; `listPublishedBranchKeys` и
  `findPublicationDir` учитывают `local/` (бейдж «рука», защита вложенности).
- [x] 8.2 Promotion `local/ -> sync/` copy-changed по манифестам (копировать
  новые/изменённые, удалить убранные, `manifest.json` + `changelog.json`
  последними); каталог `sync/` на месте всё время (без swap-окна);
  `mv local -> sync` запрещён.
- [x] 8.3 `changelog.json` (append-only, схема из `06` §2.5): дописка при каждой
  публикации по диффу `local-old vs local-new`; едет в `sync/`.
- [x] 8.4 Дисциплина двух коммитов: коммит 1 только `local/<...>`
  (`"<branchId> v<N>: <title>"`), коммит 2 только `sync/<...>`
  (`"mirror <branchId> v<N>"`) с гардом `publicationVersionComplete`
  (битое не коммитить); сообщения вместо глобальных «Снимок sync».
  Попутно исправлен `GitWrapper::shellQuote` (одинарные кавычки —
  сообщения больше не режутся по первому пробелу).
- [x] 8.5 Восстановление: у владельца первично из `local/` (перепромоут без
  git), вторично из журнала; пункты меню «Restore sync/ from local…» /
  «…from journal…»; отзыв удаляет `local/` + `sync/`.
- [x] 8.6 `.stignore` генерируется кодом в `sync/` (`*.part`, `*.tmp`,
  `.tmp-*`, `*.rev-*`); `ensureSharedDirExists` создаёт `local/`, `.tmp/`.
- [x] 8.7 UI (частично): вкладка «История» из `changelog.json` в
  `ChangeViewDialog` (передаётся `publicationDir`).
  Осталось: «Сравнить тексты» (локальная копия → HEAD); тесты: порча `sync/`
  в окне promotion, гард битого коммита, кумулятивный дифф через 3 версии.

Приёмка: сборка никогда внутри `sync/`; `sync/` восстанавливается из `local/`
без git; битое состояние в `.git` не попадает; подписчик видит историю версий
и полный дифф заметки (локальная копия → HEAD).

## Риски и контрмеры

| Риск | Контрмера |
|------|-----------|
| Внешний `git` как зависимость | вызывается только runtime через `CommandRunner`; без git — дифф/импорт/детект работают на диджестах, журнал/восстановление — с подсказкой |
| Рост `.git` от бинарных вложений | предупреждения, «архивировать историю» (сброс/GC журнала), `.gitattributes -delta` |
| Повреждение `.git` репликацией | git вне Syncthing (общая папка — только `sync/`); запись в `.git` — только само приложение, последовательно |
| Удаление/порча `sync/` | восстановление первично из `local/` (без git), вторично из локального журнала `shared/.git` (последний целостный); потеря всего `shared/` — только внешний бэкап |
| Публикация в опасной зоне | сборка в `shared/.tmp/`, авторитет `local/`, promotion copy-changed (каталог `sync/` на месте, manifest последним); `mv local -> sync` запрещён |
| Ошибочный/вредоносный контент публикации | автоприменения нет; всё через diff + подтверждения; удаления через корзину |
| Потеря локальных правок при импорте обновления | снапшот-хеши + диалог «заменить / сохранить обе» |
| Расшифровка при публикации | явное согласие владельца + предупреждение |
| Конфликт ID при импорте | новые локальные id/dir при создании; карта отображения |
| Два владельца на одной ветке | запрещено архитектурно: пишет только владелец публикации; подписчики — через импорт |
| Syncthing конфликтует в `shared/` | только владелец пишет свою `sync/<ownerDir>/<branchId>/`; иное — задокументировать как ограничение |
