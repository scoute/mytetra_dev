# MyTetra — глоссарий и журнал принятых решений (ADR)

> Документ: `08_glossary.md`
> Правила: каждое зафиксированное решение — запись даты, контекста, сути,
> следствий. Новые решения добавлять в конец.

## 1. Глоссарий терминов

| Термин | Значение |
|--------|----------|
| **БД (база данных)** | личный каталог базы MyTetra (`tetradir`): `mytetra.xml` + `database.ini` + `base/` |
| **ветка / узел (branch / node)** | элемент дерева `<node>` в `mytetra.xml` с поддеревьями и таблицей записей |
| **запись (record)** | конечная заметка в `<recordtable>`, хранится в `base/<dir>/` |
| **фрагмент ветки** | поддерево: метаданные + подветки + записи; «кусок БД» для обмена |
| **local-first** | личная БД — единственный источник правды владельца; реплицируется никогда |
| **публикация (publication)** | каталог `shared/sync/<ownerId>_<ownerName>/<branchId>_<name>/` (без каталога владельца — если профиль не настроен) с фрагментом (`branch.xml`), записями (`records/`) и `meta.json`; ключи — `<ownerId>` и `<branchId>` до первого `_` в своих сегментах |
| **подписка (subscription)** | read-only запись в панели «Подписки», связанная с публикацией |
| **baseline** | снимок публикации (манифест: фрагмент `branch.xml` + sha256 текстов записей), на который ориентируется подписчик («что я видел/импортировал»); хранится в `subscriptions.ini` как `baselineSnapshot` |
| **локальный журнал (`shared/.git`)** | единый per-machine репозиторий истории всех публикаций; вне Syncthing; источник восстановления `sync/` |
| **изменение (change)** | единица разности baseline→HEAD (запись добавлена/изменена/удалена…) |
| **импорт** | ручной перенос выбранных изменений в личную БД подписчика |
| **владелец (owner)** | участник, опубликовавший ветку и единственный пишущий в свою `shared/<ownerId>_<ownerName>/` |
| **`shareddir`** | каталог обмена (по умолчанию `<каталог бинарника>/shared`, настраивается) |
| **GitWrapper** | модуль вызова внешнего `git` через `CommandRunner` |
| **snapshotHash** | хеш локальной импортированной записи (для детекта локальных правок) |
| **карта записей (recordsMap)** | в коде реестра подписок: `sharedRecordId → { localRecordId, snapshotHash }` (в `subscriptions.ini` — `records/`) |
| **BranchDiffEngine** | чистый модуль: разница двух фрагментов (записи/ветки), без БД и UI |
| **SubscriptionImportEngine** | применение выбранных изменений к личной БД (создание/замена/удаление записи с проверками) |
| **ChangeViewDialog** | диалог «Что изменилось»: список изменений, чекбоксы, детали, «Применить выбранное»/«Отметить просмотренным» |

## 2. Зафиксированные решения

### ADR-001 (ОТМЕНЁН) — Дизайн командной работы v1

- **Дата:** 2026-09-12
- **Решение:** «федеративные ветки» + единый писатель в общем реплицируемом
  каталоге БД.
- **Статус:** отменено 2026-09-13 (см. ADR-007). Анализ показал, что
  master-master в рамках Syncthing + whole-file `mytetra.xml` принципиально не
  решаемо безопасно.

### ADR-002 — Запись mytetra.xml — только атомарно (temp + rename)

- **Дата:** 2026-09-12
- **Контекст:** `KnowTreeModel::save()` неатомарен (move в корзину → создание).
- **Решение:** в командном режиме — запись через временный файл + `rename` без
  переноса в корзину; в одиночном режиме — сохранить текущее поведение под
  конфиг-флагом.
- **Следствия:** актуально и для личной БД (устойчивость), и для публикации
  (целостность фрагментов). В подписочной модели конфликтов общей БД нет, но
  атомарность остаётся в списке техдолга.

### ADR-003 — database.ini исключён из репликации

- **Дата:** 2026-09-12
- **Решение:** никогда не синхронизировать `database.ini` (машинно-локальные
  криптоданные). В подписочной модели это достигается автоматически: БД вне
  обмена.

### ADR-004 — Политика шифрованных веток при обмене

- **Дата:** 2026-09-12
- **Решение:** шифрованная ветка **не публикуется «как есть»**. Публикация —
  только в расширенной форме (как штатный экспорт, образцу
  `exportRelatedDataAndDecryptIfNeed`) с явным согласием владельца; или ветка
  помечается «непубликуемой».
- **Следствия:** у подписчиков нет болт-объектов; дифф и импорт работают с
  открытым фрагментом.

### ADR-005 — Идентификация узла

- **Дата:** 2026-09-12
- **Решение:** `ownerId`/`nodeId` — `U<UniqueId>` (отдельное от веток
  пространство), создаётся лениво при первой публикации, хранится в профиле
  (`conf.ini`). При импорте записей генерируются новые локальные `id`/`dir`,
  ведётся карта `sharedRecordId → localRecordId`.
- **Следствия:** риск коллизий ID между машинами закрыт (переносимые ID
  используются только в пространстве публикации и не копируются в личную БД).

### ADR-006 — Legacy «внешняя команда синхронизации» остаётся

- **Дата:** 2026-09-12
- **Решение:** механизм `synchrocommand` (rsync и т. п.) остаётся как legacy;
  подписочная модель — отдельная функциональность. Общая точка — только
  `CommandRunner` (для git тоже используем его).
- **Следствия:** не ломаем существующий UX и конфиг.

### ADR-007 — Подписочная модель + local-first (v2, ЗАМЕНЯЕТ ADR-001)

- **Дата:** 2026-09-13
- **Контекст:** master-master несостоятелен; владелец уточнил направление:
  «Основная БД так и остаётся. При шаринге ветки — экспорт в отдельную папку
  `shared` … синхронизируется через Syncthing … подписываются только желающие …
  не редактировать напрямую … импорт вручную».
- **Решение:**
  1. БД участников local-first, никогда не реплицируются;
  2. обмен — каталог `shared/` (один каталог Syncthing), где живут публикации
     веток;
  3. подписчик видит read-only подписку с именем владельца в панели
     «Подписки» (вне дерева БД — его формат не меняется);
  4. импорт изменений — только вручную и выборочно.
- **Следствия:** целый класс проблем (whole-file конфликты, мониторинг,
  координация) исчезает; новая работа — публикация/подписка/дифф/импорт.
  Детали в `05`, `06`, план в `07`.

### ADR-008 — Внешний git — инструмент версионирования обмена

- **Дата:** 2026-09-13
- **Контекст:** нужно «что изменилось» с историей и авторами; собственная
  реализация журнала/снапшотов избыточна (сравнение в `06`, раздел 4).
- **Решение:** в `shared/<ownerId>_<ownerName>/<branchId>_<name>/` —
  **per-branch git-репозиторий** (один
  автор — владелец). Вызовы — `GitWrapper` (через `CommandRunner`). Git не знает
  наш формат: семантику даёт `BranchDiffEngine`.
- **Следствия:** новая runtime-зависимость (внешняя, вызываемая по желанию);
  без git доступен только просмотр среза; кнопка «архив истории» для роста `.git`.

### ADR-009 — Автоимпорт запрещён (включая автосогласие с удалениями)

- **Дата:** 2026-09-13
- **Контекст:** риск залить ошибку или нечаянно согласиться с удалением.
- **Решение:** изменения **только предлагаются**; импорт — ручное действие с
  подтверждениями. Удаления (`record.delete`, `branch.delete`) — «опасные»,
  по умолчанию не отмечены, требуют явного согласия, удаляемые локальные данные
  сначала переносятся в корзину подписчика.
- **Следствия:** использование обмена безопасно от «чужих правок в моей БД».

### ADR-010 — Подписанные ветки только для чтения

- **Дата:** 2026-09-13
- **Решение:** подписка в панели «Подписки» читается из `shared/`
  на лету; редактирование/удаление/создание внутри неё заблокировано; изменения
  можно получить только через явный импорт в личную БД.
- **Следствия:** заведомо исключаются гонки подписчик↔владелец; упрощается
  модель согласованности.

### ADR-011 — Имя владельца в метаданных и в подписке

- **Дата:** 2026-09-13
- **Решение:** профиль (`teamname`, `teamemail`) → `meta.json` публикации
  (`ownerName`, `ownerEmail`) → git-identity → метка подписки «Название —
  Имя Владельца» + тултип.
- **Следствия:** подписчик всегда знает источник; основа для будущих
  уведомлений «обновил <имя>».

### ADR-012 — Отписка не удаляет импортированные копии

- **Дата:** 2026-09-13
- **Решение:** отписка убирает только запись подписки; уже импортированные в
  БД копии остаются как обычные данные. Удаление публикации владельцем также не
  затрагивает импортированные копии у подписчиков.
- **Следствия:** безопасность местных данных максимальна; нет «культурного
  шока» при отписке.

### ADR-013 — Имя каталога публикации `<branchId>_<name>`

- **Дата:** 2026-09-13
- **Контекст:** пожелание владельца: «имя экспортируемой ветки должно содержать
  её id + её имя» (для читаемости публикаций в проводнике и Syncthing).
- **Решение:** сегмент каталога публикации внутри каталога владельца называется
  `<branchId>_<имя ветки>/`. Машинный ключ — часть `branchId` до первого `_`;
  имя — санитизированная копия названия ветки, фиксируется при первой
  публикации и не меняется при переименовании ветки (актуальный заголовок — в
  `meta.json.title`).
- **Следствия:** распознавание публикации всегда по `branchId`-префиксу;
  переименование ветки не приводит к переименованию каталога (иначе ломались
  бы подписки и Syncthing видел бы удаление+создание).

### ADR-014 — Каталог владельца `<ownerId>_<ownerName>`

- **Дата:** 2026-09-13
- **Контекст:** пожелание владельца группировать публикации по авторам:
  «изменить на `shared/owner/<branchId>_<name>/`». Литеральная папка `owner/`
  бесполезна (общая на всех); `ownerName`-одному — нестабильна при
  переименовании профиля.
- **Решение:** публикация живёт в `shared/<ownerId>_<ownerName>/<branchId>_<name>/`.
  Машинный ключ владельца — часть `ownerId` до первого `_` (зеркалит ADR-013);
  `<ownerName>` — санитизированное имя из профиля, фиксируется при первой
  публикации владельца и не меняется при переименовании в профиле (актуальное
  имя — в `meta.json.ownerName`). Если профиль не настроен — фоллбэк на плоскую
  `shared/<branchId>_<name>/` без каталога владельца.
- **Следствия:** watcher и индекс подписок сканируют/индексируют два уровня
  (владелец → публикация); `sharedPath` подписки включает каталог владельца;
  правило «владелец пишет только в свою `shared/<ownerId>_<ownerName>/`»
  закрепляется структурой каталога.

### ADR-015 — Разделение `shared/sync/` и единого локального `.git`

- **Дата:** 2026-09-13
- **Контекст:** per-branch `.git` внутри каталогов публикаций реплицировался
  Syncthing и мог быть повреждён синхронизацией/частичной записью; подписчик
  не мог полагаться на git-историю владельца (гонки, потеря при потере `.git`).
- **Решение:** двухзональный макет — `shared/sync/` (область данных, единственная
  общая папка Syncthing) и единый локальный репозиторий `shared/.git` (журнал
  состояний всех публикаций, вне Syncthing). Diff и импорт строятся на
  манифесте диджестов в `subscriptions.ini` без git; git — локальный журнал
  и источник восстановления `sync/`.
- **Следствия:** повреждение `.git` репликацией исключено; «кто изменил» — из
  `meta.json`, а не коммитов; восстановление `sync/` из журнала; работа без git
  для diff/импорта.

### ADR-016 — Авторитет `local/`, promotion copy-changed, changelog, два коммита

- **Дата:** 2026-09-15
- **Контекст:** сборка версий шла в `.tmp-*` внутри `sync/` (опасная зона,
  видит Syncthing), обновление — через `rename final -> .rev-*` + `rename tmp
  -> final` (окно «публикация исчезла»); коммит шёл после выкладки без проверки
  целостности (окно «данные без журнала», риск битого коммита); истории версий
  для подписчика не было (только накопительный дифф baseline→HEAD без
  промежуточных v и без полных текстов).
- **Решение:**
  1. `shared/local/` — авторитет владельца (не синкается, дубль 2x принят как
     меньшее зло); `shared/.tmp/` — сборка и бэкапы (вне `sync/`, та же ФС);
     `shared/sync/` — только зеркало (единственная папка Syncthing);
  2. поток: сборка в `.tmp/` → rename в `local/` → коммит 1 только `local/`
     (`"<branchId> v<N>: <title>"`) → promotion copy-changed в `sync/`
     (новые/изменённые скопировать, убранные удалить, `manifest.json` +
     `changelog.json` последними, каталог на месте) → коммит 2 только `sync/`
     (`"mirror <branchId> v<N>"`) с гардом `publicationVersionComplete`;
  3. `mv local -> sync` запрещён (теряет авторитет без git, фрагментирует
     историю по двум путям, не убирает swap-окно);
  4. `changelog.json` в публикации (append-only, схема в `06` §2.5) — история
     версий для подписчика (факты без старых контентов); полный текст
     «было/стало» — парой «локальная копия → HEAD»;
  5. восстановление у владельца первично из `local/` (без git), вторично из
     журнала; `.stignore` в `sync/` генерируется кодом.
- **Следствия:** экспорт вне опасной зоны; битое в журнал не попадает;
  подписчик видит историю версий; диск 2x в steady-state (git-дедуп blob'ов —
  журнал почти не растёт от дубля).

### ADR-017 — Фантомные корни журнала и маршрутизация импорта по веткам-копиям

- **Дата:** 2026-09-16
- **Контекст:** (1) после введения `sync/.stignore` предложение «восстановить
  из журнала» стало вечным: `journalPublicationRoots` считал корнем любой путь
  (`sync/.stignore` → корень `sync/.stignore`), которого нет среди публикаций
  диска, — восстановление ничего не чинило; (2) обновления/удаления записей
  во вложенных ветках-копиях молча пропускались: цикл импорта применял всё
  к корневой таблице копии, а `BranchDiffEngine` не заполнял `branchId`
  у record-изменений.
- **Решение:**
  1. корнем журнала считается только каталог с `meta.json` в срезе;
  2. `buildChangeList` проставляет родительскую shared-ветку у
     `RecordAdd/RecordUpdate/RecordDelete`; цикл импорта резолвит таблицу
     приёмника через `branchesMap` (корень — фолбэк).
- **Следствия:** промпт восстановления появляется только при реальной потере;
  удаления/обновления вложенных записей работают; записи из новых
  неимпортированных подветок создаются в корневой копии (до структурного
  импорта).

### ADR-018 — Структурный импорт дерева (ветки, а не только записи)

- **Дата:** 2026-09-16
- **Контекст:** диалог «Что изменилось» показывал структуру серым без
  чекбоксов, а цикл импорта писал всё в корневую таблицу копии: дерево
  владельца у подписчика не воспроизводилось.
- **Решение:**
  1. `buildChangeList` проставляет родительскую shared-ветку у record-изменений;
     цикл импорта резолвит таблицу приёмника через `branchesMap`;
  2. `applyBranchAdd/Rename/Move/Delete`: создание под ближайшим отображённым
     предком, переименование, перемещение (`TreeItem::relinkTo` +
     `KnowTreeModel::moveBranchToParent` с `beginMoveRows`/`endMoveRows` и
     защитой от циклов), удаление штатным `deleteItemsByModelIndexList`
     (файлы — в корзину, карты подписки чистятся); корень подписки не трогается;
  3. порядок применения — порядок строк диалога (ветки раньше записей);
     baseline продвигается только при полном применении.
- **Следствия:** дерево воспроизводится целиком; записи из новых
  неимпортированных подветок — в корневой копии (фолбэк); ядро формата
  не затронуто (методы аддитивны).

### ADR-019 — Каноническая сериализация branch.xml

- **Дата:** 2026-09-16
- **Контекст:** каждая автопубликация поднимала версию с пустым `changes`
  (v9→v10→v11…): `buildBranchXmlFromMytetraXml` писал `QDomDocument::toString()`,
  а порядок атрибутов в QDom случаен для каждого процесса — байтовое сравнение
  (guard пустых обновлений, манифест) видело «изменение» там, где его нет.
- **Решение:** запись через `QXmlStreamWriter` с сортированными атрибутами
  (пропуск пробельных текстовых узлов, `<!DOCTYPE mytetradoc>` сохраняется).
- **Следствия:** пустые версии прекратились (проверено живьём: v14 —
  последний переходный bump, дальше тишина); парсеры нечувствительны к порядку
  атрибутов, формат совместим.

### ADR-020 — Остаточный diff подписки (pendingChanges)

- **Дата:** 2026-09-16
- **Контекст:** после импорта диалог и срез показывали старые данные, как
  будто импорта не было: baseline двигался только при 100% применении, а
  частичное применение нигде не запоминалось (плюс `Skipped` навсегда
  блокировал продвижение).
- **Решение:** диалог/срез строят остаточный diff — свежий baseline→HEAD
  минус отражённые в живой копии (сверка текста из файлов без побочных
  эффектов + полей + структуры) минус применённые удаления (`appliedDeletes`
  в реестре, чистятся при продвижении baseline). Полный импорт → пусто,
  частичный → только остаток. Маршрутизация приёмника вынесена в
  `SubscriptionImportEngine::resolveTable` (включая поиск таблицы, где запись
  реально живёт, — чинит наследие корневой таблицы).
- **Следствия:** применённое больше не показывается; пропущенное (в т.ч.
  опасные удаления) продолжает показываться; ручное удаление копии
  подписчиком — снова предлагается как новое.

### ADR-021 — Гард удалений и красная секция среза

- **Дата:** 2026-09-16
- **Контекст:** (1) цикл импорта проверял `isRecordComplete` и для удалений,
  а для удалённой записи он всегда false (файлов нет в HEAD) — удаление молча
  пропускалось вечно, ветка исчезала, а заметка висела в повторном импорте;
  (2) в срезе удалённое было видно только строкой в заголовке.
- **Решение:**
  1. гард целостности применяется только к `RecordAdd/RecordUpdate`;
  2. в срезе — красная секция «Удалено владельцем» с плейсхолдерами веток
     и записей (красный жирный, тултипы, пояснение по клику).
- **Следствия:** удаления сходятся (проверено harness: ветка+заметка →
  пустой остаток); срез явно показывает «было, а теперь нет».

### ADR-022 — Построчный diff текста при импорте

- **Дата:** 2026-09-16
- **Контекст:** в деталях изменения было лишь «текст изменён владельцем» —
  непонятно что именно. Старое/новое доступно: HEAD из `sync/`, старое —
  живая локальная копия (baseline хранит только sha).
- **Решение:** `libraries/TextDiff` (Qt-only, Myers O(ND) с лимитами,
  рендер hunks красное/зелёное): сравнение по текстовым строкам (HTML счищен
  через XML-разбор с regex-фолбэком); картинки в тексте — строками
  `[изображение: src]` (добавление/удаление видно); вложения — только
  списками +/- (бинарное содержимое не сравнивается никогда).
- **Следствия:** решение «импортировать или нет» принимается по факту;
  движок отдаёт тексты (`headRecordText`/`localRecordTextForChange`), диалог
  рендерит; при недоступности текстов — прежняя строка-заглушка.

### ADR-023 — MCP-сервер поверх stdio (без HTTP на Qt5)

- **Дата:** 2026-09-16
- **Контекст:** нужен доступ ИИ-агентов к базе; в Qt 5.15 нет `QHttpServer`,
  HTTP с нуля — недели работы (парсер, auth, параллелизм).
- **Решение:** stdio-MCP (`mytetra --mcp`, JSON-RPC/NDJSON, протокол 2024-11-05,
  7 инструментов чтения/записи); stdout — только протокол; запрет старта при
  запущенном GUI (один писатель whole-file БД); свежий `reload()` перед
  вызовом; шифро — отказ; `--db-path` только в памяти; досрочный sync конфигов
  (`syncAndDisableExitSync` — запись из деструкторов падает на мёртвом codec).
  HTTP — только на Qt6 с общим диспетчером.
- **Следствия:** совместимость со всеми MCP-клиентами сразу; формат БД
  не меняется; правки ядра аддитивны (null-guard `insertNewRecord`,
  два `syncAndDisableExitSync`). Детали — `09_mcp.md`.

### ADR-024 — Housekeeping-инструменты MCP + TagSuggester

- **Дата:** 2026-09-16
- **Контекст:** большая БД руками не чистится; нужны move/rename/delete,
  аудит (дубликаты, пустые ветки, неразмеченные) и подсказка тегов.
- **Решение:** 10 новых MCP-тулов; `move_note` сохраняет id (карты подписок
  валидны, новый dir); удаления — в корзину + чистка карт подписок;
  `TagSuggester` (TF-IDF + RU-стемминг, Qt-only, юнит-тест); `<style>`/`<script>`
  вычищены из `TextDiff::htmlToTextLines` (иначе CSS-мусор в топе подсказок).
- **Следствия:** ИИ-агент может разбирать завалы типовым сценарием
  (аудит → suggest → подтверждение → применение); удаления — только с явного
  согласия пользователя на стороне клиента. Детали — `09_mcp.md`.

### ADR-025 — Игнор conflict-копий Syncthing + подсказки в UI

- **Дата:** 2026-09-17
- **Контекст:** `*.sync-conflict-*` могли попасть в манифест, показаться
  левой публикацией или быть молча удалены promotion как «лишние»;
  про обмен нигде в интерфейсе не рассказывалось (доки не читают).
- **Решение:**
  1. конфликты исключены из `publicationDataFiles` (единая точка, её же
     использует запись манифеста), поиска, списков и ключей; promotion
     их не трогает; разруливает человек в файловом менеджере;
  2. подсказки в UI вместо (части доки): страница «Команда» (что синкается),
     пустые подписки (проверь `sync/`), успех публикации (`sync/` разойдётся),
     тултипы «ожидания данных».
- **Следствия:** конфликт не ломает обмен и не теряется тихо; базовые знания
  о модели — в интерфейсе. Полная дока Syncthing — следующим заходом.

### ADR-026 — Тихий git журнала обмена

- **Дата:** 2026-09-17
- **Контекст:** внутренности git сыпались в консоль пользователя
  («Непроиндексированные изменения после сброса: D …») — это отчёт пустого
  `git reset` при несостоявшемся снимке журнала; так же шумели commit/checkout.
  Причина: `QProcess::execute` наследует stdout процесса.
- **Решение:** `CommandRunner::runSimpleQuiet()` (перехват и отброс вывода,
  возврат кода) для всех вызовов без захвата в `GitWrapper::runGit`;
  плюс `git reset -q` поясом с подтяжками.
- **Следствия:** журнал молчит; диагностика ошибок — через qDebug/возвраты.

### ADR-027 — Предупреждение о размере журнала вместо автосжатия

- **Дата:** 2026-09-17
- **Контекст:** журнал растёт каждым снимком (~40 КБ/коммит на текстовой базе,
  больше с вложениями); вопрос — автосжимать на N коммитах или предупреждать.
- **Решение:** тихого автосжатия нет осознанно (удаление истории необратимо
  и убивает глубину восстановления). Вместо этого: счётчики коммитов в скобках
  в пунктах меню журнала + предупреждение при ≥1000 снимков (один раз за сессию,
  с размером в МБ и кнопкой «Архивировать»). Существующий механизм
  «Архивировать историю» переиспользован; git auto-gc упаковку делает сам.
- **Следствия:** пользователь видит рост и решает сам; сюрпризов нет.

### ADR-028 — Журнальные пункты только у своих

- **Дата:** 2026-09-17
- **Контекст:** пункты Restore/Archive показывались везде, включая чужие
  подписки, где они бессмысленны; а restore чужого из журнала опасен —
  воскресил бы отозванную владельцем публикацию вопреки Syncthing.
- **Решение:** блок журнала (Restore from local/journal, Archive) — только
  пустая область, группы и свои публикации; `local/` содержит только своё,
  так что там всё честно. Чужим — только подписка/просмотр/импорт.
- **Следствия:** меню подписок короткие и понятные; риск тихого воскрешения
  отозванного закрыт.

### ADR-029 — Веб-клиппер без новых зависимостей, вставка штатным путём

- **Дата:** 2026-09-17
- **Контекст:** нужен быстрый захват фрагментов веба в `unsorted_notes`
  по глобальному хоткею; X11-заголовков в сборке нет, Wayland/Windows
  глобальный хоткей Qt не даёт.
- **Решение:** `Clipper`: X11 только через `dlopen("libX11.so.1")`
  (нет линкуемой зависимости; вне X11 — только кнопка «Clip now»);
  вставка тем же путём, что ручное создание (`insertNewRecord`,
  нормализация через `QTextDocument`, PNG как вложения); дедуп sha256
  нормализованного HTML против свежих 2000 текстов; id ветки в
  `clipperbranchid` (миграция v35→v44). Тест E2E — на настоящей модели
  через `setTestModel()`, т.к. `TreeScreen.cpp` в тесты не линкуется.
- **Следствия:** Qt-only сборка сохранена; повторный клип не плодит дубли;
  переименование ветки не ломает привязку. Побочно вскрыта гонка
  static-deinit: `QSettings::sync()` в деструкторе AppConfig после смерти
  QApplication падает в QTextCodec — в тестах лечится явным sync до выхода;
  боевому выходу нужен тот же аудит (follow-up).

### ADR-030 — DnD веток: эксперимент откачен, баг невидимости не раскрыт

- **Дата:** 2026-09-23
- **Контекст:** была попытка добавить перетаскивание веток мышью
  в `KnowTreeView` (mime `mytetra/branches`, перемещение через
  `KnowTreeModel::moveBranchToParent` с предупреждениями, переводы).
  Попутно чинены: поиск `TreeScreen` через `find_object` (parent вида —
  QSplitter, а не TreeScreen), падение в `dragMoveEvent` на пустом месте.
- **Баг:** после любого перемещения ветка исчезает из UI до рестарта;
  модель и `mytetra.xml` при этом корректны (рестарт всё возвращает).
  Живой лог с диагностикой показал: `dropEvent` доходит, перемещение
  успешно, сейв успешен, `movedIndex` валиден, `setCurrentIndex`
  срабатывает (панель записей переключается), ресетов/перезагрузок
  модели и падений после — нет.
- **Решение:** все правки вида откачены, ветка без DnD; модельный
  `moveBranchToParent`/`relinkTo` оставлен (нужен MCP и импорту подписок,
  покрыт `TestTreeModel`). Исключены статикой и тестом на живом
  `QTreeView`: сама модель, связка модель–вид, делегат, прокси/фильтры,
  вотчер каталога, сейв, подсветка DnD.
- **Следствия / задел для возврата:** остались непроверенными — содержимое
  панели записей сразу после броска, раскрыт ли приёмник, свёрнут ли вид
  в stale-layout (кандидат-фикс: `doItemsLayout()` после перемещения).
  Для будущей отладки: `qDebug` не виден в консоли, пока в
  «Настройки → Разное» не включена печать отладочных сообщений
  (`printdebugmessages`), иначе живой лог пуст и вводит в заблуждение.
