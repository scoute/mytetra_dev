# Протокол синхронизации MyTetra `sync/1`

Статус: действующий протокол линии `develop-v1-sync` (1.44.338+).
Эталон для клиентов (MyTetroid/Gee12 и др.). Обе реализации сверяются
с этим документом; расхождения — баг, чинится по месту обнаружения.

Роли: **хаб** (десктоп MyTetra, слушает порт) и **спок** (клиент,
инициирует сессию). Роли симметричны: одна программа умеет и то и другое.

## 1. Транспорт

- HTTP/1.1 поверх TCP, по умолчанию порт **47777**. Одно соединение —
  один запрос — один ответ — закрытие. Keep-alive нет.
- Тела — JSON, UTF-8. Бинарные данные (тексты заметок, аттачи) —
  строки **base64** в JSON-полях.
- TLS нет (LAN-протокол). Подлинность — HMAC-доказательства, см. §3.
- Неизвестные ключи JSON обязаны игнорироваться обеими сторонами
  (правило расширения протокола; поле `spaceId` зарезервировано
  для версии с пространствами, сейчас его нет вовсе).

## 2. Версии

Три версии, первые две — в `/hello`:

| Поле | Что | Правило |
|---|---|---|
| `proto` | версия протокола | строго `sync/1` |
| `app` | `мажор.минор` приложения | обязаны совпадать (микро — нет) |
| `format` | `мажор.минор` формата БД (сейчас `1.2`) | обязан совпадать |

Несовпадение → отказ `version-mismatch`.

## 3. Идентичность и секрет

- **deviceId** — 64 hex-символа, генерируется один раз, хранится
  в конфиге. Публичен, ходит в открытом виде.
- **Фингерпринт** — `SHA256(deviceId)` hex в верхнем регистре,
  группами по 4 через пробел. Для сверки человеком; криптографической
  силы не несет (вычислим из deviceId).
- **Секрет пары** — из общего PIN, детерминированно с обеих сторон:
  `secret_hex = SHA256(first + second + pin)`, где first/second —
  deviceId, отсортированные лексикографически. По сети не ходит.
- **Кольцо пар (4–5 устройств)**: секрет попарный, поэтому у каждого
  пира свой секрет. Хранятся в конфиге `syncDevices/<id>/secret`
  (+ легаси-пара `syncPairingSecret`/`syncPairedDeviceId` — первая
  пара, входит в кольцо для совместимости). Добавление второго
  устройства НЕ затирает первое; удаление — точечное.
  Сервер проверяет proof секретом заявившегося пира, клиент в hello
  перебирает кольцо и запоминает рабочий секрет для data-маршрутов.
  По проводам формат не менялся (тот же HMAC от тех же полей).
- **HMAC** — `HMAC-SHA256(key, challenge)` hex, ключ = байты из
  hex-секрета (`QByteArray::fromHex` / `javax.crypto.Mac` HmacSHA256).

## 4. Маршруты

| Маршрут | Назначение | Auth |
|---|---|---|
| `GET /ping` | живость: `{service:"mytetrasync", proto:"sync/1", app:"м.м"}` | нет |
| `POST /hello` | рукопожатие (§5) | proof в теле |
| `POST /manifest` | манифест хаба (§7) | data-auth |
| `POST /pull-note` | заметка целиком | data-auth |
| `POST /pull-branch` | ветка целиком | data-auth |
| `POST /push-note` | принять заметку | data-auth |
| `POST /push-branch` | принять ветку | data-auth |
| `POST /push-delete` | принять удаление | data-auth |
| `POST /commit` | сейв базы хаба | data-auth |

Ошибки маршрута данных — JSON `{error: "...", detail: "..."}` с тем же
HTTP 200 (коды HTTP не кодируют ошибки приложения).

## 5. `/hello`

Запрос:

```json
{"proto":"sync/1","app":"1.44","format":"1.2",
 "deviceId":"<64hex>","deviceName":"mint22-pc","groupId":"<16hex|пусто>",
 "clientTime":1794732685404,
 "proof":"<HMAC hex | пусто>",
 "pairRequest":true}
```

- `proof = HMAC(secret, ASCII(clientTime) + deviceId)`; пусто —
  секрета еще нет (первое знакомство).
- `pairRequest:true` — «хочу в пару»: хаб пишет входящий запрос
  (для кнопки Accept) и отвечает `pairPending:true`.
- `groupId` — сеть; пусто = девственное устройство.

Ответ:

```json
{"ok":true,"serverTime":...,"skewMs":...,"paired":true,
 "deviceId":"<хаб>","deviceName":"...","groupId":"...",
 "error":"...","detail":"...","warning":"...","pairPending":true}
```

Проверки хаба (порядок: от дешевого к дорогому):

1. **version-mismatch** — §2.
2. **foreign-network** — группы разные и обе непусты.
3. **clock-skew** — `|clientTime - serverTime| > 1000` мс.
4. **auth-failed** — секрет у хаба есть, proof не сошелся.
5. **self-hello** — `deviceId` клиента = `deviceId` хаба.

Клиент обязан продублировать проверку self-hello по `deviceId` из
ответа: синк на собственный адрес запрещен.

Особые состояния (поле `warning` при `ok:true`): хаб мог перевывести
секрет по PIN («починка пары») — клиент в ответ делает то же самое
своим PIN, чтобы сойтись к одному секрету.

## 6. Data-auth (все маршруты кроме hello/ping)

В тело запроса добавляются поля:

```json
"_dev":"<deviceId клиента>","_ts":1794732685404,
 "_proof":"<HMAC hex>"
```

`_proof = HMAC(secret, ASCII(_ts) + _dev + route)`, где `route` —
строка маршрута с методом, например `"POST /manifest"` (маршрут в
challenge — чтобы proof с pull нельзя было переподставить в push).

Проверка хабом: секрет есть; поля непусты; `|now - _ts| <= 5000` мс;
proof сошелся. Отказы: `not-paired` (секрета/привязки нет),
`auth-failed` (detail: `missing auth fields` / `stale request` /
`bad proof`). Любой отказ data-маршрута — фатален для сессии.

## 7. Манифест

`POST /manifest` → `{branches:{...}, notes:{...}, tombstones:{...}}`

```json
"branches": {
  "<id>": {"parent":"<parentId|пусто>","mtime":1794732685404,
           "hash":"<hex>","fields":{"id":"...","name":"...", ...}} },
"notes": {
  "<id>": {"branch":"<branchId>","mtime":...,"hash":"<hex>",
           "fhash":"<hex>","crypt":false,
           "fields":{"id","name","author","url","tags","ctime",
                     "dir","file","crypt"? ,"block"?},
           "attaches":[{"id":"...","file":"<имя>","type":"file|link",
                        "link":"","size":123,"hash":"<hex>"}]} },
"tombstones": { "<id>": 1794732685404 }
```

- `parent`/`branch` пусты для корневого уровня (не `"0"`!).
- Поля строковые; пустые `crypt`/`block` не передаются (канон §8).
- Незнакомые поля в `fields` — как есть (round-trip, не терять!).

## 8. Хеши (канон)

- **hash заметки** = SHA256 сырых байтов файла текста (для шифрованной —
  шифртекст как лежит).
- **fhash заметки** = SHA256 канона полей + `branch=<branchId>\n`.
- **hash ветки** = SHA256 канона полей + `parent=<parentId>\n`.
- **hash аттача**: типа `file` — SHA256 байтов файла; типа `link` —
  SHA256(UTF-8 строки цели).

Канон полей: поля по возрастанию ключа; строка `ключ=значение\n`;
значения с `crypt`/`block` == `"0"` трактуются как пустые; **пустые
значения пропускаются** (отсутствующий атрибут == пустая строка == "0"
для crypt/block).

Равенство заметок: `hash` == `hash` И `fhash` == `fhash` И наборы
аттачей равны (совпадают id с хешами; имена/размеры не сравниваются).

## 9. Заметка/ветка целиком

**pull-note** `{id}` → (поля §7 + `crypt` + `text`):

```json
{"id":"...","crypt":false,"fields":{...},"mtime":...,"hash":"...",
 "text":"<base64 сырых байтов>",
 "attaches":[{"id","type","file","link","size","data":"<base64|пусто>"}]}
```

**dirFiles** (опционально) — прочие файлы каталога заметки (инлайн-картинки
и т.п.): про них нет данных в `mytetra.xml`, без явной передачи они не
доезжают вовсе:

```json
"dirFiles": [{"file": "<имя в каталоге>", "data": "<base64>"}]
```

Все файлы каталога, кроме текста и файлов аттачей. Принимающая сторона
пишет их слепо и зеркально убирает в корзину лишние, НО только если поле
прислано (у старых пиров его нет — их локальные файлы не трогаются).
Хеш заметки остается текстовым: HTML включает ссылки на картинки, любое
изменение картинок меняет текст -> пересинк; сами файлы картинок
неизменяемы (редактор пишет их только при отсутствии).

**push-note** — то же + `"branch":"<куда>"` + auth-поля. Правила:
id сохраняется; поля пишутся слепо (шифртекст как есть, без пароля);
`mtime`/`hash` — присланные (принимающая сторона их **адоптирует**,
не «сейчас»); файлы текста/аттачей пишутся атомарно; тип `link`
файлов не создает (только строка таблицы).

Ответы: `{ok:true}` либо `{error:"..."}` (`bad request`, `no branch`,
`bad record dir`, `crypt change unsupported`, `no text`,
`no attach file`, `record lost`, `cannot write text/attach`).
Ошибка одной записи не рвет сессию (кроме auth/transport).

**pull-branch** `{id}` → `{"id","parent","fields","mtime","hash"}`.
**push-branch** — то же + auth. Смена шифрования через синк запрещена
(`crypt change unsupported`); `parent` отличается — перелинковка
(циклы запрещены).

**push-delete** `{id, deletedAt}` + auth. Удаление ветки каскадит
в tombstone на все подветки; записи поддерева покрыты tombstone'ами
веток. Идемпотентно (нет на месте — tombstone все равно пишется).

**commit** → хаб пишет `mytetra.xml` и перезагружает модели.

## 10. Правила плана (сверка манифестов)

Спок: `plan = compare(local, remote, isHub=false)`.

- Хеш равен → пропуск.
- Оба есть, хеши разные → побеждает **больший mtime**; равные —
  **хаб** (спок качает).
- Есть только на хабе → download; только локально → upload.
- **Tombstone против правки**: правка новее удаления → воскрешение
  (upload/download); иначе удаление (`deleteLocal`).
- **Tombstone ветки покрывает поддерево**: чужое под нашим удаленным
  (и наше под чужим удаленным) не переносится.
- Свой tombstone, которого нет у хаба → `pushTombs` (иначе удаление
  как единственное изменение не уедет никогда).
- Порядок применения: ветки (родители раньше детей) → записи →
  удаления → push tombstone'ов.

## 11. Порядок сессии

```
hello → [pair-логика] → fetch manifest → build local manifest
→ plan → push branches → push notes → pull branches → pull notes
→ apply deleteLocal → push pushTombs → commit (хаб) → save (себе)
```

Гейт пары: сессия, создавшая/починившую пару, данными не занимается
(`Pair established, run sync again`) — сначала пара, потом данные.
Фатально для сессии: транспорт умер, `not-paired`, `auth-failed`.
Остальные ошибки поштучные (в отчет, идем дальше).

## 12. Журнал сайдкара (референс)

MyTetra хранит локальное состояние синка в `mytetra.sync` рядом
с `mytetra.xml` (JSON; формат внутренний, но семантика — часть
протокола, ее надо держать одинаково):

- `entries: id -> {mtime, hash, kind}` — `mtime` мс последнего локального
  сейва ИЛИ адоптированное значение пира (поэтому mtime сопоставимы
  между устройствами!); `hash` — см. §8.
- `tombstones: id -> deletedAt` — пишутся при удалении и адоптируются
  из `push-delete`.
- Приоритет журнала: `mtime`/`hash` из журнала важнее файлового времени;
  потерянный журнал (нечитаемый файл) = потеря tombstone'ов и риск
  воскрешения удаленного.

## 13. Ограничения `sync/1`

- Порядок записей/веток внутри родителя не синхронизируется.
- Иконки веток — только путь, байты картинок не едут.
- Аттачи типа `link` переносятся строкой цели; клиенты, не умеющие
  `link`, обязаны сохранять атрибут как есть (round-trip), а не терять.
- Атрибут `block` («заблокированная запись») — часть формата: ходит
  в `fields`, клиенты обязаны сохранять как есть.
- Шифрованные записи/ветки — слепо: шифртекст как есть, пароль не
  ходит никогда. Клиент без пароля умеет синкать такие данные.
  Клиент МОЖЕТ прятать зашифрованные элементы локальной настройкой
  («Синхронизировать шифрованные ветки», по умолчанию вкл): фильтр
  обязан быть симметричен для обоих манифестов (иначе молчаливое
  воскрешение исчезнувшего), а tombstone'ы не фильтруются никогда
  (удаление должно доехать до пира). Поведение клиента —
  `docs/sync-behavior.md`.
- Инлайн-картинки ездят в `dirFiles` (см. §9); триггер пересинка —
  изменение HTML-текста заметки (файлы картинок неизменяемы).
- Одновременная правка одной записи с двух сторон = побеждает большее
  mtime, проигравшая версия теряется (конфликт-копии — версия v2).
